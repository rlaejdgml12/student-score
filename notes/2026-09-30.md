# 2026-09-30 (수) — 11주차: 객체지향설계 02 SOLID (1~34절: 개요·SRP·OCP·LSP)

## 🏗 OOD 02 SOLID

### SOLID 개요 (1~7절)
- (SOLID 다섯 원칙이 각각 던지는 질문) SRP는 「바뀌는 이유가 하나인가」, OCP는 「기존 코드를 고치지 않고 기능을 추가할 수 있는가」, LSP는 「자식이 부모의 약속을 깨지 않는가」, ISP는 「클라이언트가 쓰지 않는 기능에 의존하지 않는가」, DIP는 「정책이 구체 구현이 아니라 추상에 의존하는가」를 묻는다.
- (SOLID를 절대 규칙처럼 쓰면 안 되는 이유) SOLID는 컴파일러가 강제하는 규칙이 아니라 설계를 판단하는 기준이다. 과하게 적용하면 클래스와 인터페이스만 늘어나 오히려 읽고 고치기 어려워진다.
- (변경 축이라는 관점) 「무엇이 어떤 이유로 따로 바뀌는가」를 기준으로 코드를 나누는 관점이다. 같이 바뀌는 것은 모으고, 따로 바뀌는 것은 떼어 놓는다.

### SRP (8~15절)
- (SRP의 정의 — 「메서드 하나」가 아니라 무엇 하나인가) 클래스가 바뀌는 이유(변경 이유)가 하나여야 한다는 원칙이다. 메서드 개수나 기능 개수가 아니라 변경 이유의 개수로 판단한다.
- (변경 이유와 변경 주체) 코드를 바꾸라고 요구하는 사람이나 팀이 곧 변경 이유다. 가입 규칙은 기획, 메일 문구는 마케팅, 저장 방식은 DB 담당처럼 요구 주체가 다르면 이유가 다르므로 떼어 놓는다.
- (회원 서비스 위반 예제 — 한 클래스에 들어 있던 일 네 가지) MemberService 하나가 가입 규칙 검사, DB 저장, 환영 메일 발송, 감사 로그 기록을 모두 직접 해서, 하나를 고칠 때 다른 기능을 건드릴 위험이 컸다.
- (책임 분리 개선 — 인터페이스 세 개와 register가 하는 일) MemberRepository·WelcomeMessageSender·AuditLogger 인터페이스를 생성자로 주입받고, register는 Member 생성 → 저장 → 메일 → 로그의 순서만 정한다. 실제로 어떻게 하는지는 각 구현이 안다.
- (서비스가 객체 여러 개를 호출하면 SRP 위반인가 — 판단 기준) 호출 개수로 판단하지 않는다. 메서드 안에 SQL·HTTP 호출·환불 계산식 같은 세부 작업 코드가 직접 들어 있으면 위반 가능성이 높고, 순서만 정하고 일을 위임하면 위반이 아니다.
- (SRP와 응집도 / 트랜잭션 서비스) 같은 이유로 바뀌는 것끼리 모여 있으면 응집도가 높다. 트랜잭션 서비스는 여러 객체를 묶어 한 흐름을 조율하는 책임 하나를 가지므로 호출이 많아도 SRP 위반이 아니다.
- (SRP를 지나치게 적용한 경우 — 나눌지 판단하는 기준) 이메일 검사 규칙 하나하나를 클래스로 쪼개는 식의 과한 분리는 흐름을 여러 파일로 흩어 놓는다. 따로 바뀌는가, 따로 테스트할 가치가 있는가, 재사용되는가, 이름 붙일 만한 책임인가를 보고 해당하지 않으면 한 흐름으로 모아 둔다.

### OCP (16~24절)
- (OCP의 정의 — 무엇에 열려 있고 무엇에 닫혀 있나) 새 기능 추가(확장)에는 열려 있고, 기존 핵심 정책 코드의 수정에는 닫혀 있어야 한다는 원칙이다. 변경은 새 구현 추가나 조립 지점으로 한정된다.
- (switch 할인 계산기가 위반 가능성이 높은 이유) 할인 종류가 늘 때마다 switch에 case를 추가하고 계산 코드를 고쳐야 해서, 기존 코드가 계속 수정되고 다른 할인까지 깨질 위험이 있다.
- (정책 객체로 개선 — DiscountPolicy와 DiscountCalculator) interface DiscountPolicy { long discount(long price); }를 만들고 VipDiscountPolicy·CouponDiscountPolicy가 각각 구현한다. DiscountCalculator는 생성자로 DiscountPolicy를 받아 policy.discount(price)만 부르므로, 새 할인은 구현 클래스만 추가하면 된다.
- (좋은 추상화와 나쁜 추상화) 좋은 추상화는 「할인한다」처럼 잘 바뀌지 않는 안정된 역할이다. 나쁜 추상화는 구현 세부를 그대로 옮기거나 기능마다 메서드가 늘어나 모든 구현을 함께 고쳐야 하는 것이다.
- (OCP에서도 변경이 남는 곳 — 조립 지점) 어떤 구현을 쓸지 고르는 곳(@Configuration의 @Bean 메서드에서 return new RateDiscountPolicy(10); 같은 줄)은 바뀌어도 된다. 핵심 정책 코드가 닫혀 있으면 OCP를 지킨 것이다.
- (Spring Bean 조립과 OCP) @Component 스캔, @Profile, @Conditional, @Qualifier, @Primary로 핵심 코드를 고치지 않고 구현을 바꿔 끼울 수 있다.
- (OCP를 과도하게 적용한 경우) 구현이 하나뿐이고, 바뀔 가능성이 낮고, 외부 시스템과의 경계도 아니면 인터페이스 없이 구체 클래스로 두는 편이 낫다.

### LSP (25~34절)
- (LSP의 정의 — 하위 타입의 대체 가능성) 상위 타입 자리에 하위 타입을 넣어도 호출자가 기대한 행동(약속)이 깨지지 않아야 한다는 원칙이다.
- (직사각형/정사각형 반례 — is-a를 무엇으로 판단하나) Square가 Rectangle을 상속하면 resize(4, 5) 후 넓이 20이라는 부모의 약속이 16으로 깨진다. is-a는 사전적 분류가 아니라 행동 호환성으로 판단하며, 해결은 Shape 인터페이스와 불변 record 두 개로 나누는 것이다.
- (컴파일이 된다고 LSP를 지킨 것이 아닌 이유 — 정기예금 예제) 컴파일러는 시그니처만 확인한다. Account는 「출금할 수 있다」고 약속했는데 FixedDepositAccount가 withdraw에서 UnsupportedOperationException(지원하지 않는 연산이라는 예외)을 던져 약속을 깨도 컴파일은 된다.
- (정기예금 문제의 해결 — 역할 분리) Account(잔액 조회)와 WithdrawableAccount extends Account(출금 추가)로 역할을 나누고, 입출금 통장은 WithdrawableAccount, 정기예금은 Account만 구현한다. 지원하지 않는 기능을 억지로 물려주지 않는다.
- (사전조건·사후조건·불변식 — 자식이 하면 안 되는 것) 자식은 사전조건(입력 요건)을 더 까다롭게 만들면 안 되고, 사후조건(결과 보장)을 약하게 만들면 안 되며, 불변식(항상 참인 조건)은 그대로 지켜야 한다. 자바는 이를 검사하지 않으므로 계약 테스트와 리뷰로 확인한다.
- (예외 계약 — 던져도 되는 예외와 안 되는 예외) 부모 문서에 약속된 예외는 자식이 던져도 되지만, 약속에 없는 예상 밖의 예외(UnsupportedOperationException 등)를 던지면 호출자의 흐름을 깨므로 위반이 될 수 있다.
- (반환값 의미 계약 — PricePolicy) finalPrice는 0 이상, 원가 이하라는 의미 계약이 있다. 음수나 원가보다 큰 값을 돌려주면 타입은 long으로 맞아도 사후조건 위반이다.
- (컬렉션과 LSP — List.of의 add 예외는 왜 위반이 아닌가) List 문서에 add가 선택적 연산(지원하지 않으면 UnsupportedOperationException을 던질 수 있음)이라고 적혀 있어 계약 안의 동작이다. LSP는 모든 구현이 똑같아야 한다는 뜻이 아니라 문서가 허용한 범위 안에서만 달라야 한다는 뜻이다.
- (계약 테스트 — 구조와 createPolicy) 공통 테스트를 인터페이스 DiscountPolicyContract의 default 메서드로 만들고, 구현별 테스트 클래스는 createPolicy()만 public으로 구현한다. 새 구현이 생겨도 같은 시험지(할인액 0 이상, 가격 이하, 0원이면 0, 음수 가격 거부)를 그대로 풀게 된다.
- (계약 테스트가 보장하지 못하는 것) Long.MAX_VALUE 근처 값, 계산 중 오버플로, 비율 0%·100%, 고정 할인액이 가격보다 큰 경우 같은 경계값과 구현별 계산 공식·반올림 규칙·예외 메시지는 각 구현의 별도 테스트로 검증해야 한다.
