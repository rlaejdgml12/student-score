## ☕ 고급3 11 병렬 스트림과 주의점

- (parallelStream이 stream과 다른 점) JDK 구현은 둘 다 `StreamSupport.stream(spliterator(), 플래그)`이고, 마지막 병렬 플래그만 `false` → `true`로 바뀐다. "병렬로 하겠다"는 표시 하나를 켜는 것뿐이고, 어떻게 쪼갤지는 `spliterator()`가 정한다.
- (분할 → 병렬 처리 → 병합) 데이터를 여러 조각으로 나누고, 각 조각을 다른 스레드가 동시에 처리한 뒤, 부분 결과를 합친다. 분할과 병합 모두 비용이 들기 때문에, 데이터가 충분히 크고 요소당 연산이 무거워야 그 고정 비용을 넘어선다.
- (공용 ForkJoinPool) 병렬 스트림은 스레드를 직접 만들지 않고 **JVM 전체가 공유하는** `ForkJoinPool.commonPool()`을 빌려 쓴다. 기본 워커 수는 `코어 수 - 1`이고, 호출한 스레드도 작업에 참여한다. 한 곳이 이 풀을 오래 점유하면 같은 풀을 쓰는 다른 병렬 작업이 전부 밀린다.
- (병렬이 항상 빠르지 않은 이유 여섯 가지) ① 데이터가 작다 ② 연산이 가볍다 ③ 분할 비용이 크거나 자료구조가 분할에 불리하다 ④ 병합 비용이 크다 ⑤ 순서 유지가 필요하다 ⑥ 공용 풀에서 다른 작업과 경합한다. 전부 "이득 < 분할·병합·경합 비용"이라는 한 부등식의 변주다.
- (분할 비용이 자료구조마다 다른 이유) `trySplit()` 비용이 다르다. 배열·`ArrayList`·`IntStream.range`는 중간 인덱스를 한 번에 계산하므로 O(1)이지만, `LinkedList`는 가운데 노드를 찾으려고 `next`를 n/2번 따라가야 해서 O(n)이고 캐시 지역성도 나쁘다.
- (병렬에서 공유 가변 상태를 건드리면 안 되는 이유) `ArrayList.add`는 `elementData[size] = e; size++`가 하나로 묶여 있지 않다. 여러 워커가 같은 `size`를 읽으면 같은 칸에 덮어써서 원소가 **조용히 누락**되고, `null`이 섞이거나 `ArrayIndexOutOfBoundsException`이 나기도 한다. 결과가 실행마다 달라지는 경쟁 상태다. 해법은 `forEach`로 바깥에 쌓지 말고 `toList()`·`collect()`로 수집하는 것.
- (toList로 수집해도 남는 위험) 수집 그릇은 안전해지지만 담기는 **요소 자체가 가변 객체**이고 람다가 그 상태를 고치면 여전히 경쟁 상태가 생긴다. 안전의 기준은 "`toList`를 썼는가"가 아니라 "람다가 스트림 바깥의 무엇도 건드리지 않는가"(무상태·비간섭)다.
- (순서 유지 비용) `forEachOrdered`·`findFirst`·`limit`·`skip`처럼 "몇 번째"가 의미를 갖는 연산은, 먼저 끝난 조각이 앞 조각을 기다렸다가 자리를 맞춰야 해서 추가 비용이 든다. 순서가 필요 없으면 `forEach`·`findAny`·`count`가 훨씬 빠르다. `findFirst`와 `findAny`가 갈라지는 것은 병렬일 때뿐이다.
- (블로킹 I/O를 병렬 스트림에 넣으면 안 되는 이유) 응답을 기다리는 동안 CPU는 놀면서 워커만 점유된다. 공용 풀 워커는 코어 수만큼뿐이라 금세 고갈되고, 애플리케이션 전체의 병렬 작업이 멈춘다. ForkJoinPool은 "짧게 CPU를 쓰는 작업"을 전제로 설계됐다. I/O는 별도 스레드 풀이나 `CompletableFuture`로.
- (웹 서버에서 단일 요청 시간과 전체 처리량이 맞바뀌는 이유) 웹 서버는 이미 요청마다 스레드를 붙여 병렬로 돈다. 그 안에서 또 병렬 스트림을 쓰면 한 요청이 코어를 전부 끌어다 쓰므로, 그 요청은 빨라져도 **다른 요청이 쓸 CPU를 빼앗는다**. 8코어에서 요청당 300ms(코어 1개)면 초당 약 26건인데, 120ms(코어 8개)로 바꾸면 초당 약 8건으로 떨어진다. 없던 성능을 만든 게 아니라 재분배한 것이다.
- (측정 후 적용) 추측하지 말고 실제 데이터·실제 부하로 전후를 측정해 이득이 확인될 때만 적용한다. 지표는 네 가지 — 단일 요청 처리 시간, 전체 처리량, 동시 요청 수·CPU 사용률, 공용 풀 경합. 앞의 둘은 결과이고 뒤의 둘은 원인이다. `System.nanoTime()` 한두 번은 JIT 워밍업과 GC가 섞여 못 믿으므로 JMH나 실부하 테스트를 쓴다.

## ☕ 고급3 12 람다·스트림 종합실습과 면접질문

- (record compact 생성자) 괄호와 매개변수 목록이 없는 `public Student { ... }` 형태. 매개변수는 record 선언부를 그대로 쓰고, **내가 쓴 검증이 먼저 실행된 뒤** 컴파일러가 `this.id = id;` 같은 필드 대입을 자동으로 붙인다. 그래서 검증에서 예외가 나면 필드 대입까지 가지 못하고 **객체가 아예 만들어지지 않는다.**
- (반환 타입을 정하는 방법) 파이프라인 마지막 연산이 무엇을 돌려주는지 보면 된다. `filter`는 타입을 유지하고, `map(Student::name)`에서 `Stream<Student>`가 `Stream<String>`이 되며, `toList()`가 `List<String>`을 만든다.
- (Comparator 다중 기준 — reversed 위치) `reversed()`는 **그 시점까지 조립된 비교기 전체**를 뒤집는다. 점수만 내림차순이고 이름은 오름차순이려면 `comparingInt(Student::score).reversed().thenComparing(Student::name)`처럼 `thenComparing()` **앞**에 놓아야 한다. 뒤에 붙이면 이름까지 내림차순이 된다.
- (average의 반환 타입과 orElse를 메서드 안에서 쓰지 않는 이유) `IntStream.average()`는 `OptionalDouble`을 돌려준다. 메서드 안에서 `orElse(0.0)`을 하면 "실제 평균 0점"과 "응시자 없음"을 구분할 수 없게 된다. 메서드는 사실만 돌려주고, 없을 때 무엇을 할지는 **호출하는 쪽이 정한다.** `findById()`가 `Optional`을 돌려주는 이유와 같다.
- (max·min에 넘기는 것, 동점자 처리) `Comparator` 하나만 넘긴다(`max(Comparator.comparingInt(Student::score))`). `sorted`와 달리 전체 순서를 만들 필요가 없어 `reversed()`도 `thenComparing()`도 붙지 않는다. 동점자가 여럿이어도 **한 명만** 돌려주므로, 공동 1등을 모두 보려면 최고점을 먼저 구한 뒤 그 점수로 `filter`한다.
- (기본형 특화 Optional과 객체용 Optional) 숫자를 담으면 `OptionalInt`·`OptionalDouble`, 객체를 담으면 `Optional<T>`. `average`가 `OptionalDouble`인 것은 `IntStream`에서 계산한 `double`이라서이고, `highest`가 `Optional<Student>`인 것은 객체를 담아서다. 굳이 `Optional<Double>`로 감싸면 박싱 비용만 생긴다.
- (groupingBy의 다운스트림) 두 번째 인자로, 같은 키에 모인 값들을 **어떻게 쌓을지**를 정한다. 없으면 `List`로 모이고, `counting()`이면 개수, `averagingInt(Student::score)`면 평균이 된다.
- (toMap과 Function.identity) `toMap`은 키를 뽑는 함수와 값을 뽑는 함수를 받는다. `Function.identity()`는 `s -> s`와 같은 `Function<T, T>`로, "변환 없이 요소 자신을 값으로 쓴다"는 의도를 드러낸다. 매개변수가 없는 `() -> s`(Supplier)와 혼동하지 않는다.
- (toMap 중복 키) 키가 겹치면 `IllegalStateException: Duplicate key ...`가 난다. 조용히 덮어쓰지 않고 멈추는 설계다. 해법은 세 번째 인자로 **병합 함수**를 주는 것 — `(existing, replacement) -> existing`이면 먼저 온 것 유지, `-> replacement`면 덮어쓰기. 안전해지는 이유는 "덮어쓰기라서"가 아니라 **정책을 코드에 명시했기 때문**이다. `groupingBy`는 키가 겹치는 것을 전제하고, `toMap`은 안 겹치는 것을 전제한다.
- (orElse vs orElseGet — 평가 시점) `orElse(makeDefault())`는 인자를 먼저 계산하므로 값이 있어도 `makeDefault()`가 **항상 실행**된다. `orElseGet(Class::makeDefault)`는 만드는 방법(Supplier)을 넘기므로 **비었을 때만 실행**된다. 기본값 생성이 DB 조회나 API 호출이면 `orElse`는 필요 없는 요청을 매번 날린다.
- (스트림 재사용) 스트림은 한 번 흘러가는 물줄기다. 최종 연산이 끝나면 닫히고, 다시 쓰면 `IllegalStateException: stream has already been operated upon or closed`가 난다. 결과가 두 가지 필요하면 원본 컬렉션에서 `stream()`을 **두 번 부른다.** 스트림을 변수에 담아 두는 것은 오히려 위험 신호다.
- (스트림이 적합한 경우 / 반복문이 적합한 경우) 필터·변환·정렬·그룹화·집계처럼 **"무엇을 할지"가 분명한 데이터 처리**는 스트림이 명확하다. 복잡한 상태 전이, 여러 조기 종료(`break`)나 다단계 예외 처리, 체인이 지나치게 길어질 때, 단계별 디버깅이 중요할 때는 반복문이 낫다. 스트림에는 `break`가 없어 억지로 흉내 내면 바깥 변수를 건드리게 되고(변수 캡처 제약 때문에 배열이나 AtomicBoolean 같은 꼼수), `forEach` 안의 `return`은 `break`가 아니라 `continue`라 실제로 멈추지도 않는다. 목표는 "가장 명확한 표현"이지 모든 반복문을 스트림으로 바꾸는 것이 아니다.
- (30초 답변 틀) **핵심 정의 → 이유·특징 → 주의점**, 세 문장이면 충분하다. 이 틀로 답하면 암기가 아니라 구조로 설명하게 되어 써 본 사람이라는 것이 드러난다.
