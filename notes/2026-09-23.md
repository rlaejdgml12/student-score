- (병렬 스트림에서 바깥 ArrayList에 add하면 생기는 일) 대부분 오류 없이 원소가 조용히 누락되고 실행할 때마다 결과가 달라진다. add 안의 「칸에 넣기」와 「size 늘리기」가 묶여 있지 않아 두 워커가 같은 칸에 덮어쓰기 때문이다. 가끔 null이 섞이거나 ArrayIndexOutOfBoundsException이 난다. 해법은 바깥에 쌓지 말고 toList()·collect()로 모으는 것.
- (toMap 병합 함수가 없을 때 키가 겹치면) IllegalStateException(Duplicate key)이 나며 멈춘다. 데이터가 조용히 사라지는 걸 막으려는 설계다. 세 번째 인자로 병합 함수를 주면 정책을 정할 수 있다 — (a, b) -> a는 먼저 온 값 유지, (a, b) -> b는 덮어쓰기.
- (Function.identity()와 같은 람다) s -> s. 받은 것을 그대로 돌려준다. toMap(Student::id, Function.identity())처럼 값 자리에 요소 자신을 넣을 때 쓴다. () -> s는 입력이 없으니 Supplier다.

## 🏗 OOD 01 객체지향 4대특징

### 객체와 협력 (1~8절)
- (객체지향의 정의 — 객체가 하는 세 가지) 프로그램을 서로 협력하는 객체들의 모임으로 보는 방식. 객체는 필요한 상태를 가지고, 책임에 맞는 행동을 하고, 다른 객체에 메시지를 보낸다.
- (메시지를 「보내는 쪽」과 「받는 쪽」을 가리는 두 단계) ① 그 줄이 어느 클래스 안에 적혀 있나 → 그 클래스가 보내는 쪽. ② 점(.) 앞에 누가 있나 → 그 객체가 받는 쪽. 매개변수·리턴값은 방향과 관계없다.
- (메서드 선언 줄은 보내는 것인가 받는 것인가) 둘 다 아니다. public void takeOrder(...) 같은 선언 줄은 「이런 메시지를 받을 수 있다」는 받는 쪽의 명찰(받을 수 있는 메시지 목록)이다. 실제로 보내는 줄은 그 안의 다른객체.메서드() 줄이다.
- (절차지향이 더 나은 경우) 작은 계산, 단순한 변환, 알고리즘(코테의 BFS·정렬 등)처럼 입력을 받아 결과만 내는 코드. 지켜야 할 상태와 규칙이 있으면 객체로 묶는다.
- (setBalance 대신 deposit을 두는 이유) setBalance는 아무 값이나 받아 잔액을 바꿀 수 있고 규칙을 넣을 자리가 없다. deposit은 무엇을 하는지 이름에 드러나고, 「0 이하 입금 금지」 같은 규칙을 그 안에서 객체가 직접 지킨다.
- (좋은 설계를 따져 보는 여섯 질문) 객체가 자기 상태를 스스로 지키는가 / 책임이 명확한가 / 구현 세부 사항이 밖으로 새지 않는가 / 변경되는 부분이 분리되어 있는가 / 다른 구현으로 교체할 수 있는가 / 테스트하기 쉬운가. 4대 특징은 이 질문을 해결하는 수단이다.
- (네 특징이 서로 맞물리는 방식) 추상화가 역할을 정하고(DiscountPolicy), 다형성이 그 역할에 여러 구현을 바꿔 끼우고(Rate·Fixed), 캡슐화가 각 구현의 내부를 보호하고(private percent + 검증), 상속은 타입 관계·재사용이 필요한 일부에만 제한적으로 쓴다.

### 캡슐화 (9~20절)
- (캡슐화와 정보 은닉의 차이 — 자판기 비유) 정보 은닉은 덮개 — private으로 내부를 못 보고 못 만지게 하는 것. 캡슐화는 규칙 있는 버튼 — 상태를 규칙과 함께 묶어 의미 있는 행동으로만 바꾸게 하는 것. private + 규칙 없는 setter는 은닉만 있고 캡슐화는 없고, public 필드 + 규칙 있는 cancel()은 캡슐화만 있고 은닉이 없어 우회당한다.
- (IllegalArgumentException과 IllegalStateException 구분법) 인자만 보고 틀렸다고 알 수 있으면 Argument(음수 출금, 수량 0), 값은 정상인데 객체의 지금 상태 때문에 안 되면 State(잔액 부족, 이미 결제됨, 최대 레벨). 인자 없는 메서드가 거절하면 거의 항상 State.
- (protected가 다른 패키지 자식에게 허용하는 범위) this(자기 자신)나 자식 타입 참조를 통해 물려받은 자기 몫에만 접근할 수 있다. 아무 부모 타입 객체를 통해서는 접근할 수 없다. 상속 설계를 위해 제한적으로 열어 둔 것.
- (「묻고 대신 결정하지 말고 시켜라」) 서비스가 order.getStatus()로 물어보고, 취소해도 되는지 직접 판단한 뒤 setStatus(CANCELLED)로 바꾸지 말라는 뜻. 대신 order.cancel()처럼 객체에게 시키고, 취소 가능 여부 판단은 주문이 스스로 한다. 규칙이 한곳에 모이고 중복 조건이 사라진다.
- (불변식과 검사해야 할 네 지점) 불변식은 객체가 생성부터 소멸까지 언제나 만족해야 하는 규칙(잔액 0 이상, 수량 1 이상 등). 검사할 곳은 생성자, 메서드, 상태 변경, DB·파일에서 읽어 되살리는 복원 과정 네 곳.
- (final · List.copyOf · 불변 요소가 각각 막는 것 — 상자와 물건) final은 필드가 다른 상자(리스트)로 바꿔치기되는 것만 막는다. List.copyOf는 만들 때 복사본 상자를 따로 만들고 뚜껑을 잠근다 — 원본을 바꿔도 안 따라오고, 꺼낸 리스트에 add·remove·clear를 하면 UnsupportedOperationException. 그래도 상자 안 물건(OrderLine)의 setter는 막지 못하므로, 물건까지 막으려면 요소 자체를 record 같은 불변 객체로 만든다.
- (record가 해 주지 않는 것 두 가지) ① 값 검증 — compact 생성자에 직접 써야 한다. ② 안에 담긴 가변 객체(리스트 등)의 내용 불변 — List.copyOf를 직접 써야 한다. 필드 재대입 금지, 값 기준 equals/hashCode, toString은 해 준다.

### 상속 (21~29절)
- (super(name)이 꼭 필요한 경우) 생성자는 상속되지 않는다. 부모에 인자 없는 생성자가 없고, 부모의 private 필드는 자식이 직접 초기화할 수 없을 때 super(name)으로 부모 생성자에게 맡긴다. 부모에 기본 생성자가 있으면 컴파일러가 super()를 자동으로 넣는다.
- (오버라이딩과 오버로딩) 오버라이딩은 상속 관계에서 부모 메서드를 같은 시그니처로 다시 정의하는 것이고, 어느 메서드가 불릴지 실행 시점에 정해진다(다형성과 연결). 오버로딩은 한 클래스 안에 이름은 같고 매개변수가 다른 메서드를 여러 개 두는 것이고, 컴파일 시점에 정해진다.
- (CountingSet이 6을 세는 이유) 자식 addAll에서 3을 센 뒤 super.addAll을 부르는데, 부모 addAll이 내부에서 add를 하나씩 부르고 그 add가 자식이 재정의한 add라서 3을 또 센다. 자식이 부모의 내부 구현(addAll → add 호출 순서)에 묶이는 「깨지기 쉬운 기반 클래스」 문제.
- (is-a 판단 기준 — 정사각형·직사각형) 말로 「A는 B다」가 되는지가 아니라, 부모를 쓰던 자리에 자식을 넣어도 모든 코드가 그대로 맞게 동작하는지(대체 가능성)로 판단한다. 정사각형은 setHeight가 가로까지 바꿔 resize 결과가 20이 아닌 16이 되므로 상속하면 안 된다(LSP).
- (Stack이 ArrayList를 상속하면 안 되는 이유) extends하면 add(0, x)·remove(3) 같은 리스트 메서드가 전부 딸려 와서 「맨 위에서만 넣고 뺀다」는 스택 규칙이 깨진다. 리스트를 private 필드로 가지고 push·pop만 여는 조합이 맞다. 자바의 옛 Stack도 이 문제가 있어 ArrayDeque를 권한다.

### 추상화 · 다형성 (30~51절)
- (추상화 = 없애기인가 숨기기인가, 추상화 수준 맞추기) 숨기기다. 세부 사항을 없애는 게 아니라 적절한 경계 뒤로 숨기고 중요한 역할만 드러낸다. 수준 맞추기는 「결제를 승인한다」 같은 업무 규칙과 HTTP header·timeout 같은 인프라 세부 사항을 한 메서드에 섞지 않는 것.
- (추상 클래스 vs 인터페이스 선택 기준) 공통 상태(필드)·생성자·공통 구현을 나눠 주는 게 목적이면 추상 클래스, 교체 가능한 역할을 정하는 게 목적이면 인터페이스. 클래스는 하나만 상속, 인터페이스는 여러 개 구현이라는 차이도 있지만 선택 기준은 목적이다.
- (컴파일 때 검사하는 타입과 실행 때 불리는 구현) 검사는 왼쪽 변수 타입(DiscountPolicy)으로, 실행은 오른쪽 실제 객체(FixedDiscountPolicy)의 구현으로. 동적 메서드 디스패치.
- (조건문을 다형성으로 바꾸면 달라지는 것) 새 종류가 생겨도 기존 메서드를 열어 if를 추가하지 않고 구현 클래스 하나만 추가하면 된다. 종류마다 다른 상태와 검증을 넣을 자리가 생기고, 테스트도 종류별로 나뉜다. 단 어떤 구현을 쓸지 고르는 조립 지점에는 조건이 남을 수 있다.
- (sealed + switch에서 default가 필요 없는 이유) sealed ... permits PaymentSuccess, PaymentFailure로 자식을 둘로 못 박으면 컴파일러가 가능한 경우를 알기 때문에, switch가 모든 경우를 다뤘는지 검사해 주고 빠뜨리면 컴파일 오류를 낸다. 종류가 닫혀 있으면 sealed + switch, 계속 늘어나면 다형성.
- (상속과 다형성은 같은가) 다르다. 다형성은 목적(같은 상위 타입으로 여러 구현을 바꿔 쓰는 성질), 상속은 그 수단 중 하나. 인터페이스 구현, 클래스 상속, sealed 계층 모두 다형성을 만들 수 있고 실무에서는 인터페이스를 더 자주 쓴다.

### 스프링 · 백엔드 (52~70절)
- (DI란) 의존성 주입. 객체가 필요한 다른 객체를 직접 new로 만들지 않고, 바깥의 스프링 컨테이너가 만들어서 생성자 등으로 넣어 주는 것. 서비스는 역할(인터페이스)만 알고, 어떤 구현을 넣을지는 컨테이너가 정한다.
- (생성자 주입의 장점 세 가지) ① 필수 의존성이 분명하다 ② 필드를 final로 두어 만든 뒤 바뀌지 않는다 ③ 테스트에서 가짜 구현을 직접 넣을 수 있다. 「자동으로 넣어 준다」는 DI 자체의 설명이다.
- (인터페이스가 필요 없는 경우) 구현이 하나뿐이고 바뀔 일이 거의 없는 앱 내부 클래스, 의미 없는 OrderService / OrderServiceImpl 1:1 짝. 가능성만 보고 남발하지 말고 실제 변화 축(여러 구현, 외부 인프라 교체, 테스트 대역)이 있을 때 만든다.
- (도메인 객체와 서비스 객체, 빈약한 도메인 모델) 도메인 객체는 업무 상태와 규칙을 가진다(Order.cancel()이 취소 가능 여부 판단). 서비스 객체는 찾아오기 → 시키기 → 저장 → 알림 같은 작업 흐름과 트랜잭션을 조정한다. 빈약한 도메인 모델은 도메인이 getter/setter만 가지고 규칙이 전부 서비스에 몰린 모습.
- (DTO를 경계에서 변환하는 이유) 요청 DTO를 도메인까지 그대로 끌고 들어가면 API 필드 이름 같은 형식만 바뀌어도 도메인 규칙 코드까지 고쳐야 한다. 컨트롤러 경계에서 도메인 객체로 변환하면 API와 도메인이 분리되고, 변환 순간 Quantity 같은 생성자 검증도 걸린다. 모든 계층마다 기계적으로 DTO를 두라는 뜻은 아니다.
- (CompositeNotificationSender가 조합인 이유) 메일·문자 기능을 extends로 물려받는 게 아니라, 여러 발송기를 List 필드로 가지고 있다가 send에서 하나씩 일을 맡기기 때문(has-a). 자바 클래스는 부모를 하나만 가질 수 있어 상속으로는 불가능하고, 조합이면 푸시가 생겨도 목록에 하나 더 넣으면 된다. 자기도 NotificationSender를 구현해서 서비스는 단일 발송기와 묶음을 구분 없이 쓴다.
- (가짜 객체로 테스트할 수 있는 이유) OrderService가 구체 클래스를 직접 new하지 않고 DiscountPolicy 역할에만 의존하며 생성자로 받기 때문. 그 역할을 구현한 FakeDiscountPolicy도 들어갈 수 있어, 스프링·외부 API 없이 결과를 정해 놓고 서비스만 시험할 수 있다.
