## 캡스톤 백엔드 읽기 API (JdbcTemplate + Oracle)

### ① 오늘 만든 API와 요청 흐름
- 팀장 요청(10/28 14시까지 「백엔드 어디까지 했는지」)에 맞춰 읽기 API 7개를 갖췄습니다. health 2개는 기존 것이고, 새로 만든 GET은 /api/jobs, /api/jobs/{jobId}/skills, /api/summary, /api/skills, /api/trends/job-demand 5개입니다.
- 요청이 지나가는 길은 Controller(주소 매핑, 입력 확인, 응답 만들기) → Repository(JdbcTemplate으로 SQL 실행) → Oracle DB 순서이고, 응답은 record(JobSkillResponse 등)에 담아 JSON으로 돌려줍니다. 수집 DB는 SELECT만 합니다.

### ② /api/jobs/{jobId}/skills (직무별 인기 기술 상위 N개)
- @PathVariable로 jobId를, @RequestParam(defaultValue = "5")로 limit을 받습니다. limit이 1~50이 아니면 400과 code INVALID_LIMIT을, jobId에 해당하는 직무가 없으면 404와 code JOB_NOT_FOUND를 돌려주고, 성공하면 200과 JobSkillResponse를 돌려줍니다.
- JobSkillResponse 필드: jobId, name(직무 이름), calcDate(기준 날짜), jobTotal(그 직무의 공고 수), smallSample(jobTotal이 100 미만이면 true인 소규모 직무 표시), items. items의 각 항목(record Item)은 rank, skillId, name, category, percentage, postingCount입니다.
- percentage는 비율(ratio)을 Math.round(ratio * 1000) / 10.0으로 바꿔 소수 첫째 자리 퍼센트로 만듭니다(예: 0.1234 → 12.3).
- Repository 메소드는 직무 이름을 찾는 findJobName, 상위 기술 목록을 찾는 findTopSkills, 기준 날짜와 직무 공고 수를 찾는 findLatestStat 세 개입니다.

### ③ JdbcTemplate과 RowMapper
- query(sql, RowMapper, 값…)는 여러 줄을 List로 돌려주고, 결과가 없으면 null이 아니라 빈 리스트입니다. queryForObject는 정확히 한 줄이 나와야 하며 줄이 없으면 EmptyResultDataAccessException(결과 0건 예외)이, 여러 줄이면 IncorrectResultSizeDataAccessException(결과 개수가 기대와 다름)이 납니다.
- SQL의 ? 개수는 jdbcTemplate에 넘기는 값의 개수와 같고, 위에서부터 순서대로 대응합니다(findTopSkills는 jobId, limit 순서).
- RowMapper는 결과의 줄 하나를 객체 하나로 바꾸는 규칙이고, 람다 (rs, rowNum) -> … 로 씁니다. 중괄호 { }를 쓰면 return을 직접 써야 하고, 중괄호 없이 식 하나면 return이 생략됩니다.

### ④ Oracle SQL 문법 (MySQL과 다른 점)
- 상위 N개는 MySQL의 LIMIT 대신 FETCH FIRST ? ROWS ONLY를 씁니다. NVL(값, 대체값)은 NULL을 대체하는 함수이고 MySQL의 IFNULL에 해당합니다(LIMIT 대용이 아닙니다). 테이블 없이 계산만 할 때는 FROM DUAL을 씁니다.
- 테이블 별칭에 AS를 쓰면 ORA-00933(SQL 명령어가 올바르게 종료되지 않음)이 납니다. 컬럼 별칭의 AS는 Oracle에서도 됩니다.
- SQL 문자열 안의 오타(예: 컬럼명 오타)는 IntelliJ가 잡지 못하고 실행해야 ORA-00904(부적합한 식별자) 같은 오류로 드러납니다.

### ⑤ 기준 날짜 버그
- 가장 최근 통계 날짜는 전체 MAX(calc_date) 하나여야 하는데, 안쪽 서브쿼리에 WHERE job_id를 붙이면 직무마다 다른 날짜가 섞입니다. 명세는 전체에서 하나의 날짜입니다. 「돌아간다」와 「명세와 맞다」는 다릅니다. 클로드코드 검수 2회에서 이 기준 날짜, 오류 문구, 주석을 고쳤습니다.

### ⑥ 화면 연동과 푸시
- 메인 화면과 기술 트렌드 화면의 Mock 데이터를 실제 API 호출로 바꿨습니다(.jsx는 프런트엔드 파일). 커밋·푸시는 마지막에 한 번만 했고, 푸시 대상은 origin/development가 아니라 dev_KDH 브랜치입니다. 팀 카톡방에 진행 상황을 공유했습니다.

## 힘들어한 부분
- 긴 SQL(스칼라 서브쿼리, EXISTS, 3중 중첩) 읽기가 어려웠고 「쿼리문이 점점 복잡해진다, 나중에 직접 짤 수 있을까」라고 느꼈습니다.
- SQL 문자열 안 오타를 IDE가 잡지 못하는 점, 상위 N개 문법(MySQL LIMIT → Oracle FETCH FIRST)과 NVL의 역할, 「정확히 한 줄」이 필요한 조회에서 queryForObject를 고르는 것에서 틀렸습니다.
