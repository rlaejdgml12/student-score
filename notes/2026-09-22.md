## 🔁 복습 드릴 — 9/21에 막혔던 항목 16문항

### 회수한 것 (11개 — 3회 통과 카운트 1/3)

- **is-a 판단 기준** — 부모 타입이 쓰이던 자리에 자식을 넣어도 그대로 동작하는가(대체 가능성). 이름이 어색하지 않은가가 아니다.
- **List.copyOf 방어적 복사** — 밖에서 넘긴 리스트를 나중에 고쳐도 내부가 안 바뀌고, 꺼내 간 리스트에 add를 해도 예외가 난다. 단 담긴 객체 자체는 얕은 복사.
- **record가 보장하지 않는 것** — 안에 담은 리스트·객체의 *내용*까지 불변은 아니다. 필드 재대입과 값 기준 equals/hashCode/toString은 보장.
- **reversed() 위치** — `comparingInt(Student::score).reversed().thenComparing(Student::name)`. reversed()는 그 시점까지 조립된 비교기 전체를 뒤집으므로 thenComparing 앞에 둔다.
- **orElse vs orElseGet** — orElse는 값이 있든 없든 인자를 먼저 계산한다. 기본값 생성이 DB 조회면 매번 실행되므로 orElseGet(Supplier).
- **공용 ForkJoinPool** — 병렬 스트림은 JVM 전체가 공유하는 commonPool()을 빌려 쓴다. 한 곳이 오래 점유하면 다른 병렬 작업이 전부 밀린다.
- **블로킹 I/O를 병렬 스트림에 넣으면 안 되는 이유** — 응답을 기다리는 동안 CPU는 놀고 워커만 잡혀 있다. 워커는 코어 수만큼뿐이라 금세 고갈된다.
- **toMap 중복 키** — `IllegalStateException: Duplicate key`(키가 겹칠 때 나는 예외). 세 번째 인자로 병합 함수를 주면 정책이 코드에 명시된다.
- **스트림 재사용** — 최종 연산 후 닫히고 다시 쓰면 `IllegalStateException`(이미 소비된 스트림에 접근할 때 나는 예외). 원본 컬렉션에서 stream()을 두 번 부른다.
- **groupingBy 다운스트림 / Function.identity()** — 같은 키에 모인 값을 어떻게 쌓을지 정한다(없으면 List). identity()는 `s -> s`.
- **순서 유지 비용 / 분할 비용 / 스트림 vs 반복문 / 웹 서버 처리량 역설 / 값 객체** — 전부 정답.

### 아직 막힌 것 (다음 세션 복습 대상)

- ⭐⭐ **다운캐스팅이 반복될 때 의심할 것** — 2회 연속 막힘. 제네릭 문제가 아니라 **부모 타입(역할)에 필요한 행동이 없는 것**. 구분 기준: 캐스팅한 뒤 부르는 메서드 이름이 서로 다르면 역할 문제.
- **병렬에서 공유 가변 상태** — ArrayList.add는 `elementData[s] = e`와 `size = s+1`이 묶여 있지 않아 원소가 조용히 누락된다.
- **toList 이후에도 남는 위험** — 그릇은 안전해도 담기는 객체가 가변이면 경쟁 상태. 기준은 "람다가 스트림 바깥의 무엇도 건드리지 않는가".
- **상속과 다형성의 구분** — 다형성은 목적(부모 타입으로 자식을 다루기), 상속은 수단 중 하나. 인터페이스도 수단.
- **compact 생성자** — 검증이 필드 대입보다 먼저라 예외가 나면 객체가 아예 만들어지지 않는다.
- **max·min의 인자** — Comparator 하나만. 동점자가 여럿이어도 한 명만 돌려준다.
- **기본형 특화 Optional** — IntStream에서 계산한 숫자는 OptionalInt·OptionalDouble, 객체는 Optional&lt;T&gt;.
