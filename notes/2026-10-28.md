# 2026-10-28 (수) 능동회상 노트

> 능동 회상으로 채우지 못해 Claude가 정리한 자료입니다(2026-10-28 동희님 요청). 다음 복습 드릴에서 다시 회상합니다.

## 스프링 15 스프링 웹 MVC와 REST API

### ① 요청이 컨트롤러에 닿기까지 (§1)
- 요청이 지나가는 길은 필터 → DispatcherServlet → HandlerMapping(어느 컨트롤러 메소드인지 찾음, @GetMapping 등) → 인터셉터 → HandlerAdapter(메소드 인자를 채움, @PathVariable·@RequestParam·@RequestBody 해석은 HandlerMethodArgumentResolver가 담당) → 컨트롤러 → HttpMessageConverter(반환 객체를 JSON으로 바꿈) 순서입니다. 컨트롤러 밖에서 난 예외는 HandlerExceptionResolver가 받아 응답으로 바꾸고, 여기에 §5의 @RestControllerAdvice가 연결됩니다.
- 각 부품을 인터페이스로 분리해 두고 바꿔 끼울 수 있게 한 설계가 전략 오브젝트입니다. 캡스톤 JobSkillController의 @GetMapping("/api/jobs/{jobId}/skills"), @PathVariable int jobId, @RequestParam(defaultValue = "5") int limit, ResponseEntity.ok(...)가 위 단계에 하나씩 대응합니다.

### ② 매핑과 ResponseEntity (§2)
- @GetMapping·@PostMapping·@PutMapping·@PatchMapping·@DeleteMapping은 HTTP 메소드별 매핑입니다. 입력은 @PathVariable(경로의 값), @RequestParam(? 뒤의 쿼리 값), @RequestBody(본문 JSON), @RequestHeader(헤더)로 받습니다.
- ResponseEntity는 상태 코드·헤더·본문을 직접 정해 돌려줍니다: ok = 200, created(location) = 201 + Location 헤더, noContent() = 204(본문 없음이라 ResponseEntity<Void>), badRequest = 400. 고정 상태만 필요하면 @ResponseStatus를 씁니다.

### ③ 엔티티 대신 DTO (§3)
- 엔티티를 API로 바로 반환하면 네 가지 문제가 있습니다: 내부 구조가 API 스펙이 되어 엔티티를 못 바꿈 / 비밀번호처럼 감춰야 할 값이 노출됨 / 지연 로딩과 양방향 연관관계 때문에 순환 참조나 불필요한 조회가 생김 / 요청값으로 엔티티를 직접 받으면 클라이언트가 보낸 값이 엔티티를 덮어씀.
- 그래서 요청 DTO와 응답 DTO를 record로 따로 만들고, 변환(from, toUser)은 DTO 쪽에 둡니다. 캡스톤의 JobSkillResponse(record, 안에 record Item)가 응답 DTO의 예입니다.

### ④ 입력 검증 (§4)
- spring-boot-starter-validation을 넣고 DTO 필드에 @NotNull·@NotBlank·@NotEmpty·@Size·@Min·@Max·@Email·@Pattern을 붙인 뒤, 컨트롤러 인자에 @Valid를 붙입니다.
- 본문 검증에 실패하면 MethodArgumentNotValidException(본문 JSON 검증 실패 예외)이 납니다. 경로·쿼리 값의 제약 실패는 스프링 6.1부터 HandlerMethodValidationException(메소드 인자 검증 실패 예외)입니다. 클래스에 @Validated를 붙이면 6.1의 내장 검증이 꺼지고 ConstraintViolationException(제약 위반 예외)이 나며, 처리하지 않으면 500이 됩니다.
- 검증은 값만 보고 알 수 있는 형식(예: limit이 1~50인가)까지만 맡습니다. 직무가 DB에 있는가 같은 업무 규칙은 서비스에서 확인해 업무 예외(JobNotFoundException 등)를 던지고 @RestControllerAdvice가 응답으로 바꿉니다.

### ⑤ 전역 예외 처리 (§5)
- @RestControllerAdvice 클래스의 @ExceptionHandler 메소드가 예외 종류별로 응답을 한곳에서 만듭니다. 오류 본문은 ProblemDetail(RFC 9457 표준 형식)을 쓰고, ResponseEntityExceptionHandler를 상속하거나 spring.mvc.problemdetails.enabled=true로 기본 예외도 같은 형식으로 맞춥니다.
- 예상 못 한 Exception은 스택 트레이스나 SQL을 응답에 넣지 않고 로그에만 남깁니다. 시큐리티 필터에서 난 예외는 @RestControllerAdvice가 못 잡고 AuthenticationEntryPoint·AccessDeniedHandler로 처리하며(14편), 메소드 보안의 AccessDeniedException은 Exception 전체를 잡는 처리기가 있으면 500이 될 수 있습니다.
- 캡스톤의 Map.of("status", 400, "code", "INVALID_LIMIT", …)로 컨트롤러마다 오류 응답을 만드는 방식을 이 구조로 모으는 것이 11/2 「오류 응답 통일」 작업입니다.

### ⑥ 필터·인터셉터·AOP (§6)
- 필터는 DispatcherServlet 앞에서 요청·응답 원본을 다루고(인코딩, 요청 ID, 보안), 인터셉터는 DispatcherServlet 안에서 컨트롤러 앞뒤에 끼며 어느 컨트롤러인지 알 수 있고(로그인 확인, 컨트롤러 단위 로깅), AOP는 빈 메소드 호출 앞뒤에 끼는 메소드 단위 처리입니다(트랜잭션, 실행 시간, 감사 로그). 요청 단위이면서 컨트롤러를 몰라도 되면 필터, 알아야 하면 인터셉터, 메소드 단위면 AOP입니다.
- 필터에서 난 예외는 DispatcherServlet보다 앞이라 @RestControllerAdvice가 못 잡고, 인터셉터와 AOP의 예외는 잡습니다.
- RequestIdFilter(OncePerRequestFilter)는 UUID로 요청 ID를 만들어 MDC(스레드별 로그 값)에 넣고 응답 헤더에도 담은 뒤 chain.doFilter로 다음 단계에 넘기고, finally에서 MDC.remove로 지웁니다. 스레드를 재사용하므로 안 지우면 이전 요청의 ID가 다음 요청 로그에 섞입니다. 인터셉터는 WebMvcConfigurer.addInterceptors에서 addPathPatterns("/api/**")·excludePathPatterns로 거는 주소를 정하고, 필터를 특정 URL에만 걸거나 순서를 정하려면 FilterRegistrationBean으로 등록합니다.

### ⑦ 외부 API 호출 RestClient (§7)
- RestClient(스프링 6.1+)는 RestClient.Builder(Boot가 빈으로 제공)의 baseUrl로 기본 주소를 정하고 post().uri(…).body(요청).retrieve().onStatus(…).body(응답.class)처럼 메소드를 이어 붙입니다. retrieve()만으로는 요청이 나가지 않고 body(…)·toEntity(…)·toBodilessEntity() 같은 마지막 메소드를 불러야 요청이 갑니다. 4xx·5xx는 기본으로 RestClientException(REST 호출 실패 예외) 계열 예외가 되고, onStatus는 그 대신 우리 업무 예외로 바꿔 던질 때 씁니다.
- 타임아웃은 반드시 정합니다. 외부 서버가 응답하지 않으면 우리 서버의 요청 스레드와 DB 커넥션이 함께 묶여 장애가 번집니다. Boot 3.4~3.5는 spring.http.client.connect-timeout, read-timeout이고 Boot 4.0부터는 spring.http.clients.connect-timeout, read-timeout(clients, 복수)입니다.
- 서킷 브레이커·재시도(Resilience4j)는 이름만 알면 됩니다. RestTemplate은 7.0부터 사용 중단이 발표되어 RestClient.create(restTemplate)으로 감싸 차례로 옮기고, 비동기·스트리밍은 WebClient입니다.

### ⑧ 컨트롤러 테스트 (§10)
- 컨트롤러 메소드를 자바로 직접 부르면 주소 매핑, JSON 변환, @Valid 검증, @RestControllerAdvice 예외 변환이 실행되지 않아 검증되지 않습니다. @WebMvcTest(컨트롤러.class)는 컨트롤러와 웹 부품(@RestControllerAdvice 포함)만 띄워 @SpringBootTest보다 빠릅니다.
- 이때 서비스 빈이 없으므로 컨트롤러가 필요로 하는 자리를 @MockitoBean으로 가짜로 채우고, MockMvc로 mockMvc.perform(post(…).contentType(JSON).content(…)).andExpect(status().isBadRequest()).andExpect(jsonPath("$.status").value(400))처럼 요청을 흉내 내 검증합니다. 서비스가 DuplicateUserIdException(아이디 중복 업무 예외)을 던지게 해 두고 409와 code USER_DUPLICATE_ID가 나오는지 보는 테스트는 업무 예외가 @RestControllerAdvice를 거쳐 409로 바뀌는지를 검증합니다.
- Boot 4에서는 의존성이 spring-boot-starter-webmvc-test가 되고 @WebMvcTest·@AutoConfigureMockMvc가 org.springframework.boot.webmvc.test.autoconfigure 패키지로 옮겨집니다.

### ⑨ 30초 설명 (§11)
- 요청은 필터를 지나 DispatcherServlet에 들어와 HandlerMapping으로 컨트롤러 메소드를 찾고 인자 해석과 JSON 변환을 거칩니다. 응답은 엔티티 대신 DTO로 돌려주고 입력은 @Valid로 검증하며, 실패와 업무 예외는 @RestControllerAdvice에서 ProblemDetail로 통일합니다. 공통 작업은 필터·인터셉터·AOP에 성격별로 나누고, 외부 API는 RestClient에 타임아웃을 걸어 부르며, 이 모두를 MockMvc 테스트로 확인합니다.
- 보충편 §8(페이징, 스프링 데이터 JPA를 배운 뒤)과 §9(springdoc, 운영 환경에서 Swagger UI 막기)는 오늘 계획에 없어 하지 않았습니다.
