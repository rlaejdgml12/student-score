## ☕ 고급1 01 — 프로세스와 스레드

- **프로그램 / 프로세스 / 스레드** ✅
  프로그램은 설계도(아직 실행 안 된 파일), 프로세스는 그게 실행되어 자원을 할당받은 것, 스레드는 그 안에서 실제로 일하는 일꾼(실행 흐름).
  → 레시피 종이 / 주방 하나 / 그 주방의 요리사

- **프로세스끼리 vs 스레드끼리** ✅
  프로세스는 메모리가 독립돼 서로 못 건드림(대신 통신은 IPC로, 비쌈). 스레드는 같은 메모리를 공유해서 빠른 대신 서로 영향을 준다. → 요리사끼리가 더 위험하다.

- **힙 / 클래스 데이터 / 스택** 🔁 다시 볼 것
  - 힙 = **공유** (객체, 배열, 인스턴스 필드)
  - static 필드·클래스 데이터 = **공유**
  - Java 스택 = **스레드별 독립** (지역 변수, 매개변수)
  - 변수 구분법: 메서드 밖 + static → static 필드 / 메서드 밖 + static 없음 → 인스턴스 필드 / 메서드 안 → 지역 변수

- **지역 변수는 안전한가** ✅ (기준까지 정확)
  변수의 위치가 아니라 **건드리는 데이터가 공유되느냐**로 판단한다. 지역 변수 자체는 스레드마다 따로지만, 그 변수가 **가리키는 객체**가 힙의 공유 객체면 여전히 위험하다.

- ⚠️ **동시성 vs 병렬성** — 이름이 서로 바뀌어 있었음
  - **병렬성** = 양손으로 진짜 동시에 누르는 것 (코어가 여러 개, 물리적으로 같은 순간)
  - **동시성** = 한 손으로 엄청 빠르게 번갈아 눌러 동시처럼 보이는 것 (구조의 문제, 코어 1개로도 가능)
  - 외우기: **병렬(並列) = 나란히 늘어섬 = 손이 여러 개**
  - 배타적이지 않다. 보통 "동시성 있게 설계해서 병렬로 실행"한다.
  - ⭐ 동기화 문제·교착 상태는 **동시성**에서 나온다. 코어 1개에서도 터진다.

- **문맥 전환** ✅
  하던 작업을 멈추고 다른 작업으로 넘어가는 것. 레지스터·다음 명령 위치를 저장하고 복원하는 데 CPU 시간이 들고, **캐시가 무효화**된다. → 스레드를 무작정 늘리면 오히려 느려진다. (→ 고급2 스레드 풀)

- **CPU 바운드 vs I/O 바운드** 🔁 다시 볼 것
  - CPU 바운드(계산이 주력) → 코어 수 넘겨 스레드를 늘리면 손해
  - I/O 바운드(DB·네트워크 대기가 주력) → 기다리는 동안 CPU가 노니까 **스레드를 늘리면 이득**
  - 백엔드 서버 일은 대부분 I/O 바운드. 그래서 멀티스레드가 중요하다.

- **싱글턴 빈과 무상태 설계** 🔁 다시 볼 것
  싱글턴 빈은 인스턴스가 하나라 **인스턴스 필드가 힙의 공유 상태**가 된다. 요청마다 달라지는 값을 필드에 두면 다른 요청이 덮어쓴다(A가 B의 응답을 받는 사고).
  - 필드에 두면 안 되는 것: 요청으로 들어온 값, 처리 중인 주문번호, 직전 결과
  - 둬도 되는 것: **의존성**(Repository 등), 불변 설정
  - → 요청별 값은 **매개변수·지역 변수**로 (스택에 따로 생기니까 안전)

## ☕ 고급1 02 — 스레드 생성과 실행

- **스레드 만드는 3가지 방법** ✅
  Thread 상속 / Runnable 구현 / 람다

- **Thread 상속의 제약** ✅
  자바는 단일 상속이라 `extends Thread`를 쓰면 다른 클래스를 못 상속한다. (`implements`는 개수 제한 없음)

- **Runnable을 권장하는 이유 3가지** 🔁 다시 볼 것
  1. 다른 클래스를 자유롭게 상속할 수 있다
  2. **작업(무엇을)과 실행(어떻게)이 분리**된다
  3. 같은 작업을 `Thread`에도 `ExecutorService`에도 넘길 수 있다
  ⚠️ 성능 때문이 아니다. 실행 속도는 같다. 이유는 전부 **설계상의 유연성**.

- **람다가 가능한 이유 / 함수형 인터페이스** 🔁 다시 볼 것
  `Runnable`은 추상 메서드가 `run()` **하나뿐**인 인터페이스 = 함수형 인터페이스. 메서드가 하나뿐이라 컴파일러가 무엇을 구현하는지 알 수 있어서, `new Runnable() { public void run() {...} }`의 뻔한 부분을 전부 생략할 수 있다.
  `()`가 비어 있는 건 반환형이 void라서가 아니라 **run()이 매개변수를 안 받아서**.

- ⚠️ **`Runnable task = () -> ...` 에서 task에 담기는 것**
  실행 **결과**가 아니라 **객체 그 자체**. `new MyTask()`와 같은 자리다.
  → 레시피 종이 비유: 요리 결과가 아니라 **종이 자체**가 담긴다. 이 줄에서는 아무것도 출력되지 않고, `run()`을 호출해야 비로소 실행된다.
  (람다 = 클래스 정의 + 객체 생성이 한 번에 일어나는 것. 익명 클래스의 축약형)

- **실행 순서가 비결정적** ✅
  어느 스레드를 언제 실행할지는 **OS 스케줄러**가 정한다. `start()` 순서와 실행 순서는 무관.
  → `join()`이 없으면 "main 끝"이 제일 먼저 나올 수 있다.
  ⭐ 비결정성은 버그가 아니라 **전제**다. "내 컴퓨터에선 됐는데 서버에서 깨지는" 버그의 원인.

## ☕ 고급1 03 — start, run, sleep, join

- ⚠️⭐ **start() vs run()**
  - `worker.start()` → **새 스레드 생성**, 그 스레드가 `run()` 실행 → `worker-1` 출력
  - `worker.run()` → 새 스레드 **없음**. **main이 직접** 실행 → `main` 출력
  - 비유: **run = 내가 직접 요리 / start = 요리사 불러서 시킴**
  - `run()`은 그냥 평범한 메서드(`if (target != null) target.run();`이 전부). 마법은 `native void start()`에만 있다.

- **Thread 객체 vs 실제 스레드** 🔁 다시 볼 것
  `new Thread(...)`는 **힙에 자바 객체만** 만든다. 이 시점에 OS 스레드는 없다(채용 서류만 작성).
  `start()`를 호출해야 JVM이 OS에 실제 스레드를 요청한다(요리사가 주방에 들어옴).
  → `Thread` 객체는 실제 스레드를 다루는 **손잡이**. 손잡이 하나에 스레드 하나가 짝지어지므로 `start()`를 두 번 부르면 `IllegalThreadStateException`.
  → 이 제약 + 생성 비용이 **스레드 풀**의 필요성으로 이어진다.

- **sleep()은 누구를 재우나** ✅
  **호출한(실행 중인) 스레드 자신.** `worker.sleep()`이라 써도 worker가 아니라 main이 잔다 — `sleep`은 static이라 `worker`가 무시되기 때문. 그래서 항상 `Thread.sleep()`으로 쓴다.
  → 자바에는 **특정 스레드를 재우는 방법이 없다.** 남을 멈추려면 인터럽트로 협조를 구해야 한다.

- **join()은 누가 무엇을 기다리나** ✅
  `worker.join()` → **호출한 스레드(main)** 가 worker가 끝날 때까지 기다린다. 주체는 main, 대상은 worker.
  `sleep`과 구조가 같다 — 둘 다 **호출한 스레드**에 작용한다.
  (덤: `join()`은 대기뿐 아니라 **가시성**도 보장한다 → 06 volatile)

- **안티패턴 — start 하자마자 join** ✅
  `start(); join(); start(); join();` 하면 사실상 **순차 실행**이 된다(3초짜리 둘이면 6초).
  → **모두 시작 → 그다음 모두 대기** 순서를 지켜야 겹쳐 진행된다(3초).

- ⭐ **sleep은 락을 반납하는가** — 방향은 맞았고 핵심이 빠졌었음
  **반납하지 않는다.** 화장실 문 잠그고 잠든 것과 같다.
  핵심은 "CPU가 논다"가 아니라 **그 락을 기다리는 다른 스레드가 전부 묶인다**는 것. A가 3초 자면 B도 3초 못 들어와서 총 6초(직렬).
  → `synchronized` 안에 DB 조회·API 호출 같은 느린 작업을 넣으면 안 되는 이유.
  (비교: `Object.wait()`는 기다리는 동안 **락을 반납**한다)

- **sleep(1000)의 정확한 의미** ✅
  "1초 뒤에 실행된다"가 아니라 **"1초 전에는 절대 안 깨어난다"**. 깬 뒤 CPU를 언제 받는지는 스케줄러가 정한다. → 시간에 민감한 로직을 sleep으로 맞추면 안 된다.

## ☕ 고급1 04 — 인터럽트와 스레드 종료

- **Thread.stop()이 폐기된 이유** ✅ (핵심 보강)
  임의의 지점에서 강제로 죽이기 때문. 핵심 위험은 "락이 안 풀린다"가 아니라, 죽으면서 **락이 갑자기 풀려 반쯤 망가진 객체가 다른 스레드에 노출**된다는 것. (출금은 됐는데 입금이 안 된 계좌)

- **협력적 종료란** ✅
  밖에서는 `interrupt()`로 **"멈춰 달라"고 요청만** 하고, 받은 쪽이 안전한 지점에서 정리하고 스스로 끝낸다. "언제 멈춰도 안전한지는 그 작업 코드가 제일 잘 안다"는 판단.

- **이 방식의 약점** ✅
  신호를 무시하면 **못 멈춘다.** 밖에서는 구경만 할 수 있다. → "서버 종료 명령을 내렸는데 프로세스가 안 죽는" 장애.
  ⭐ 그래도 **"안 멈추는 버그"가 "데이터가 깨지는 버그"보다 낫다**는 게 자바의 판단.

- **interrupt()의 두 가지 동작** 🔁 다시 볼 것
  - 대상이 `sleep`·`join`·`wait`로 **대기 중**이면 → `InterruptedException`을 던지며 **즉시 깨어남**
  - 대상이 **실행 중**이면 → 인터럽트 **상태 플래그만 true**가 되고 실행은 계속됨
  → 그래서 대기가 없는 작업은 코드가 직접 확인해 줘야 한다.

- **대기 없이 도는 작업은 어떻게 멈추나** ✅
  ```java
  while (!Thread.currentThread().isInterrupted()) { ... }
  ```
  매 반복마다 신호를 확인한다. 루프를 빠져나온 뒤 **정리 코드가 정상 실행**된다는 게 `stop()`과의 결정적 차이.

- ⭐ **인터럽트 상태 복구** — 방향은 맞았고 목적이 달랐음
  `sleep`·`join`·`wait`가 예외를 던질 때 자바가 **인터럽트 플래그를 지운다**(예외로 알렸으니 소비했다는 논리). 그래서 catch에 들어오면 "인터럽트된 적 없는" 상태가 된다.
  다시 켜는 목적은 "한 번 더 해야 멈춰서"가 아니라 — **바깥 코드나 스레드 풀이 중단 요청이 있었다는 사실을 알아야 하기 때문**이다.
  ```java
  } catch (InterruptedException e) {
      Thread.currentThread().interrupt();   // interrupted() 아님!
  }
  ```

- ⛔ **빈 catch가 최악인 이유** ✅ (원인 보강)
  결과적으로 계속 실행되는 것도 맞지만, 근본 원인은 **중단 요청 자체가 증발**한다는 것. 예외를 던지며 플래그가 지워졌는데 아무것도 안 하면 아무도 그 신호를 모른다.

- ⚠️ **isInterrupted() vs Thread.interrupted()** — 뒤바뀌어 있었음
  **둘 다 확인용**이다. 멈추는 건 어느 쪽도 아니다.
  - `isInterrupted()` — 특정 스레드 확인만. 플래그 **안 지움** → 반복문 조건에 쓴다
  - `Thread.interrupted()` — 현재 스레드 확인 + 플래그 **지움(소비)**
  이름 구분: `interrupt()` = 켠다 / `isInterrupted()` = 확인만 / `Thread.interrupted()` = 확인+지움

## 🧩 코테 01 — 자바 빠른 입출력

- **Scanner 대신 BufferedReader** ✅
  Scanner는 값 하나마다 정규식 토큰화·타입 검사·변환을 해서 느리다. 코테는 입력 형식이 보장되니 그 검사가 필요 없다.

- **BufferedReader 세 겹 조립** 🔁 다시 볼 것
  - `System.in` — 키보드 입력 통로. **바이트** 단위
  - `new InputStreamReader(...)` — 바이트를 **문자**로 변환
  - `new BufferedReader(...)` — 문자를 **버퍼에 모아 줄 단위**로 꺼내줌 (빠른 이유가 이 버퍼)
  → "통로를 두 번 감싼다"로 기억. 외울 필요는 없고 자동완성으로 씀.

- **readLine()의 성질 3가지** 🔁 다시 볼 것
  1. 항상 **String** 반환 (숫자로 쓰려면 `Integer.parseInt`)
  2. **줄바꿈은 떼고** 준다
  3. ⭐ 한 번 읽으면 **커서가 다음 줄로**. 되돌아갈 수 없다
  (+ 입력이 끝나면 `null` 반환 → EOF 문제에서 사용)
  → **한 줄 = readLine() 한 번, 그 안의 값들 = nextToken() 여러 번**

- **StringTokenizer와 nextToken()** ✅
  공백 기준으로 조각(토큰)을 나누고, `nextToken()`으로 하나씩 꺼낸다. 꺼내면 커서가 넘어가고 되돌아갈 수 없다(Iterator와 같은 구조). 꺼낸 값은 **문자열**이라 파싱 필요.
  반복문 안에서 **매번 새로 만드는** 이유: 줄마다 내용이 다르니까.

- ⚠️ **split()과의 차이** — 뒤바뀌어 있었음
  - `split(" ")` — 정규식 기반. 연속 공백이면 **사이에 빈 문자열이 생긴다** (`"a  b"` → `["a", "", "b"]`)
  - `StringTokenizer` — 연속 공백을 **하나처럼 건너뛴다.** 빈 토큰이 안 생김
  → 그래서 코테에서 `StringTokenizer`를 더 쓴다. (`trim().split("\\s+")`도 대안)

- **StringBuilder / print vs println** ✅
  반복문 안에서 `println`을 계속 부르면 출력 호출이 쌓여 느리다. `StringBuilder`에 모아 마지막에 한 번만 출력.
  `sb`에 이미 `'\n'`이 들어 있으므로 **`print`** 를 쓴다. `println`이면 끝에 빈 줄이 하나 더 붙어 출력 형식이 틀릴 수 있다.

## 🧩 코테 02 — 시간복잡도와 입력 크기 감각

> 이 절은 대부분 기억이 안 났음. 상시 참고표 아티팩트를 열어두고 쓸 것.

- **Big-O에서 상수·계수를 버리는 이유** ✅
  N이 커질수록 최고차항이 압도해서 나머지가 묻힌다. `3N + 10` → `O(N)`, `N² + N + 100` → `O(N²)`

- **반복문 나란히 vs 중첩** ✅
  나란히 = **더하기**(큰 쪽만 남음) → `O(N)` / 중첩 = **곱하기** → `O(N²)`

- **N과 M이 다를 때** ✅
  `O(NM)`. ⚠️ `O(N²)`로 뭉개면 안 된다 — M이 N보다 훨씬 클 수 있다.

- **판단 순서 4단계** 🔁 다시 볼 것
  ① 문제에서 N의 **최댓값**을 본다 → ② 내 풀이의 복잡도를 센다 → ③ N을 대입해 연산 횟수를 구한다 → ④ **1억**과 비교한다

- **1억 기준 / N ≤ 100,000에 O(N²)** 🔁 다시 볼 것
  1초 ≈ 약 1억 회 연산(단순 정수 기준, 거친 감각).
  `100,000² = 100억` → 1억의 100배 → **시간 초과.** `O(N log N)` 이하를 찾아야 한다.
  ⭐ 거꾸로 읽는 게 실전 팁 — 문제가 `N ≤ 20`을 준 건 "완전탐색으로 풀어라"는 힌트.

- **숨은 비용 3가지** 🔁 다시 볼 것
  - `list.contains(x)` — ArrayList는 처음부터 훑어 **O(N)**. 반복문 안이면 전체 `O(N²)` → **HashSet**으로 (평균 O(1))
  - `str += "a"` — String은 불변, 매번 새로 생성·복사 → **StringBuilder**
  - `Collections.sort()` 반복문 안 — 매번 `O(N log N)`
  → **반복문 개수만 세면 틀린다.** 안에서 부른 메서드가 뭘 하는지까지 세야 한다.

- **2^N과 N!의 차이** 🔁 다시 볼 것
  - **부분집합** = 각 원소를 넣을지 말지 → `O(2^N)` → N ≤ 20까지 가능
  - **순열** = N개를 줄 세우는 모든 경우 → `O(N!)` → N ≤ 10까지
  (N=20이면 `2^20 ≈ 100만`이지만 `20! ≈ 243경`)

## 🧯 트러블슈팅

- **`Unhandled exception: InterruptedException / IOException`** — `join()`·`sleep()`·`readLine()`이 검사 예외를 던지는데 `main`에 `throws`가 없어서 발생. `public static void main(String[] args) throws IOException`으로 해결. 하루에 세 번 반복해서 만남
- **`NumberFormatException: For input string: "10 20"`** — 한 줄에 두 값이 있는데 `StringTokenizer`로 쪼개지 않고 `br.readLine()` 전체를 `Integer.parseInt`에 넣어서 발생. 에러 메시지가 문제의 문자열과 줄 번호(`Main3.java:15`)를 그대로 알려줬다
- **`Thread.currentThread().interrupted()`** — 상태 복구하려다 `interrupt()` 대신 `interrupted()`를 씀. **정반대 동작**이고 컴파일 에러도 안 나서 가장 찾기 어려운 버그
- **IntelliJ 콘솔에서 백스페이스** — 엔터를 친 줄은 이미 프로그램에 전달돼서 되돌릴 수 없다. 화면 글자만 지워지고 입력이 꼬인다. → 잘못 쳤으면 재실행하거나, 입력 전체를 미리 써두고 붙여넣기
- **`git push` → Repository not found`** — GitHub에 원격 레포를 안 만들고 `remote add`만 했음

## 💭 헷갈렸던 것 / 다시 볼 것

**⚠️ 방향이 반대로 기억됐던 것 (재복습 1순위)**
1. 동시성 ↔ 병렬성
2. `isInterrupted()` ↔ `Thread.interrupted()`
3. `split()` ↔ `StringTokenizer` (연속 공백 처리)
4. `Runnable task = () -> ...` 에 담기는 것 (결과 X, 객체 O)
5. `start()` ↔ `run()`

**🔁 기억이 안 났던 것**
- 힙/스택 공유 구조 ⭐ (8/29 05 Race Condition의 전제)
- CPU 바운드 vs I/O 바운드
- 싱글턴 빈 무상태 설계
- Runnable 권장 이유 3가지 / 함수형 인터페이스
- Thread 객체 vs 실제 스레드
- `interrupt()`의 두 가지 동작
- 코테 02 전반 (판단 4단계 · 1억 기준 · 숨은 비용 · 2^N vs N!)

**📌 세션 중 물어본 것**
- `run()`의 실제 코드가 뭔지 (→ `Thread` 클래스 내부 구조를 보고 이해)
- 람다에 반환값이 없는데 왜 `Runnable task =` 로 대입되는지
- `Thread.sleep()`이 static인데 왜 `worker.sleep()`이 컴파일되는지
- `join()`으로 막히면 새 작업을 못 받는 것 아닌지 (→ 스레드 풀·`ExecutorService`가 필요한 이유에 스스로 도달)
- 관리자 스레드와 워커 사이에 스레드 풀이라는 층이 하나 더 있다는 것

**✅ 스스로 도달한 것**
- I/O 대기 중에는 자원이 노니까 스레드를 여러 개 두는 게 이득이라는 판단
- `join()`이 블로킹이라 새 요청을 못 받는다는 지적 → 스레드 풀의 존재 이유
- `Thread` 상속이 "보기에 좋은 게 없어 보인다"는 판단 (실무 결론과 일치)
- `try`를 `while` 밖에 두어야 한다는 구조 판단
- 세 스레드 `join()`의 총 소요를 4초 → 2초로 스스로 정정
