## 고급1 08 — 동기화 주의점과 스레드 안전성

> 부제: **락을 더 거는 것보다 '공유 상태를 줄이는' 설계가 먼저다.**

- **스레드 안전(thread-safe)의 정의**: 여러 스레드가 동시에 써도 클래스의 불변 조건과 올바른 결과가 유지되는 것. ⭐ 진짜 기준은 **"호출하는 쪽이 별도의 동기화를 하지 않아도 안전해야 한다"**. "쓰는 사람이 알아서 락 걸면 안전해요"는 스레드 안전이 아니다.
- **흔한 오해**: 메서드 하나에 `synchronized`가 있으면 클래스가 안전하다 → **아니다.** 안전성은 **메서드 단위가 아니라 클래스 전체의 상태 관리**로 판단한다.
- **깨지는 두 지점**
  - ① **락을 공유하지 않는 다른 경로**: `increase()`엔 락이 있고 `get()`엔 없으면, 잠기지 않은 문이 하나 더 있는 것.
  - ② **여러 메서드에 걸친 연산**: `if (get() < 10) increase();` — 각각은 원자적이어도 **둘을 묶은 연산**은 원자적이지 않다. 락은 메서드가 끝나면 반납되므로 사이에 반드시 틈이 생긴다.
  - → 해결은 락을 더 붙이는 게 아니라 **연산 자체를 클래스 안으로 옮기는 것**(`increaseIfBelow(limit)`).
- ⭐ **우선순위 사다리 3단계**
  1. **공유하지 않기** — 공유가 없으면 동기화 자체가 필요 없다
  2. **공유하되 불변으로** — 변하지 않으면 여럿이 읽어도 안전하다
  3. **그래도 필요하면 동기화** — 락은 실패나 회피 대상이 아니라, 공유 불변 조건을 지켜야 할 때 **정상적이고 필수적인 도구**다
- **요청별 데이터는 지역 변수·매개변수로**: 지역 변수와 매개변수는 **스레드마다 각자의 스택**에 있어 동기화 없이도 안 섞인다. 필드는 힙에 하나뿐이라 모든 요청 스레드가 공유한다. → **"요청 상태는 필드가 아니라 흐름을 따라 흘려보낸다."**
- **불변 객체와 `record`**
  - `record`는 컴포넌트 참조의 **재대입**을 막지만, 컴포넌트가 **가변 컬렉션·배열**이면 **깊은 불변이 아니다**(= 얕은 불변). 바깥에서 원본 리스트를 건드리면 그대로 반영된다.
  - 해결: **압축 생성자**에서 방어적 복사. `Order { items = List.copyOf(items); }`
  - **안전한 공개(safe publication)**: 불변 객체라도 다른 스레드가 **완전히 만들어진 객체**를 보도록 전달해야 한다. 수단은 정적 초기화·`final` 필드·동기화된 전달·동시성 컬렉션.
- **과도한 동기화의 대가**: ① **처리량 하락**(상관없는 메서드끼리도 같은 `this` 락으로 줄을 선다) ② **교착 상태 위험 증가**. 공유되지 않는 지역 데이터에 락을 거는 건 비용만 늘리는 일.
- **락 범위** — 교재의 균형점: **"좁게, 그러나 필요한 만큼은 반드시."** 준비·후처리는 임계 영역 밖으로 빼되, **검사와 변경은 반드시 함께 묶는다.**
- ⛔ **락을 쥔 채 느린 I/O**: 외부 API·파일·DB 접근을 락 안에서 하면, 그 I/O가 끝날 때까지 같은 락을 기다리는 **모든 스레드가 묶여** 시스템 전체가 한 요청 속도에 발목 잡힌다. 락 밖으로 빼되, 그사이 상태가 바뀔 수 있으므로 스냅샷·버전 검증 같은 일관성 전략을 함께 설계한다.
  - ⚠️ **이미 있는 메서드를 락 안에서 재사용하면 그 메서드가 하는 일 전부가 내 락 범위로 들어온다.** (오늘 `addIfBelow`에서 `addOrder`를 부르다 `println`이 락 안으로 딸려 들어간 사고)
- **스프링 싱글턴 빈의 무상태 설계**: 빈은 **하나의 인스턴스를 여러 요청 스레드가 공유**하므로 필드는 곧 공유 가변 상태 후보다. **필드에 둬도 되는 것은 ① 의존성(다른 빈) ② 불변 설정** 두 가지뿐. 요청마다 달라지는 값과 쌓이는 가변 컬렉션은 빼야 한다.
  - 단서: 빈이 무상태여도 **협력 객체·공유 자원의 스레드 안전성은 따로 검토**해야 한다.
- **지역 변수가 가리키는 공유 객체**: 변수는 스레드마다 각자 있어도, 그 변수가 가리키는 **객체**가 공유면 여전히 위험하다. 변수를 복사한 것이지 객체를 복사한 게 아니다.
  - ⭐ 판단 기준은 **변수의 위치가 아니라 "가리키는 데이터가 공유 가변인가"**.
- **동기화 정책 문서화**: `// 이 클래스는 스레드 안전하다. count는 lock으로 보호된다` 한 줄만 남겨도, 나중에 누군가 락 없이 필드를 건드려 안전성이 무너지는 걸 막는다. 동시성 코드는 **의도를 명시하는 것**이 특히 중요하다.

### ⭐ 오늘 두 번 기울었던 것 — 가변인가 vs 컬렉션인가

> ❌ "컬렉션·배열이니까 위험하다"
> ✅ **"그게 변할 수 있는가 / 그 가변 상태를 건드리는 모든 경로가 같은 락으로 보호되는가"**

`List.of(...)`로 만든 **불변 리스트는 안전**하다. 반대로 `int[]`·`HashMap`은 `final`이어도 내용이 바뀌므로 위험하다. `final`은 **화살표만 고정**한다.

## 고급1 09 — 교착 상태(Deadlock)

- **정의**: 둘 이상의 스레드가 **서로 상대방이 가진 락을 기다리며** 아무도 나아가지 못하는 상태.
  - **경쟁 상태 = 값이 깨진다 / 교착 상태 = 실행이 멈춘다.** 예외도 로그도 없이 조용히 멈추는 게 전형적 증상.
- **순환 대기**: 스레드1 →(B를 기다림)→ 스레드2 →(A를 기다림)→ 스레드1. **대기의 화살표가 고리를 이루면** 아무도 빠져나갈 수 없다.
- ⭐ **락 획득 순서 통일**: 두 스레드가 모두 `A → B` 순서로 잡으면, A를 못 잡은 스레드는 **아무것도 쥐지 않은 상태로** 기다리므로 고리가 생기지 않는다.
  - 실무 처방: **락에 순위를 매기고 항상 낮은 순위부터.** 계좌 이체면 **계좌 ID가 작은 쪽을 먼저** 잠근다.
- **네 조건과 각각 깨는 법** (넷이 **동시에** 성립해야 교착. 하나만 깨도 예방)
  - **상호 배제** — 자원을 한 스레드만 점유 → 공유 가능 자원으로 전환
  - **점유와 대기** — 쥔 채로 추가 대기 → 필요한 락을 한꺼번에 획득
  - **비선점** — 쥔 락을 뺏을 수 없음 → 타임아웃 후 포기(`tryLock`)
  - **순환 대기** — 대기 고리가 순환 → **락 획득 순서 통일**
  - → 앞의 셋은 자바에서 깨기 어려워, **실무에서 손대는 건 사실상 순환 대기 하나**다. **네 조건은 진단 도구, 순서 통일은 처방.**
- **중첩 락 최소화**: 애초에 여러 락을 동시에 쥐지 않으면 순환 대기가 성립할 수 없다. 두 락으로 나눠 보호하던 걸 하나로 합치거나 공유 상태를 줄여 락을 없앨 수 있는 경우가 많다. → **08편의 "공유 상태 최소화·락 범위 좁게"가 교착 예방과 직결**된다.
- **스레드 덤프**: 멈춘 자바 프로세스는 `jps`로 PID를 찾고 `jstack <PID>`로 각 스레드가 쥔 락과 기다리는 락을 확인한다. JVM이 `Found one Java-level deadlock:` 으로 직접 짚어주기도 한다. 교착은 예외 없이 멈추므로 **로그로는 원인을 못 찾는다.**
- **`sleep()`이 원인이 아닌 이유**: `sleep`은 두 스레드가 각자 첫 락을 확실히 잡도록 타이밍을 벌어 교착을 **눈에 보이게** 만드는 장치일 뿐. 빼도 타이밍만 맞으면 발생한다. 진짜 원인은 **서로 다른 순서로 두 락을 중첩 획득한 구조**다.
  - ⭐ 08편 실험에서 `sleep(1)`이 버그를 **만든 게 아니라 드러냈던 것**과 같은 이치.

## 고급1 10 — 멀티스레드 종합 실습과 면접 질문

- **volatile 카운터가 실패하는 이유**: `count++`는 **읽기 → 증가 → 쓰기** 세 단계 복합 연산이라, 최신 값이 보여도 읽고 쓰는 사이에 끼어들면 갱신이 유실된다. `volatile`은 **가시성만** 준다.
  - 실측: 2스레드 × 100,000회 → **161,024** (약 4만 유실)
- **동시성 문제의 두 축**

  | 축 | 증상 | 해결책 |
  |---|---|---|
  | 가시성 | 변경이 안 보임(무한 루프 등) | `volatile` 또는 `synchronized` |
  | 원자성 | 갱신 유실·값 어긋남 | `synchronized` 또는 원자 변수 클래스 |
  | 둘 다 | 복합 연산 + 가시성 | `synchronized` |

- ⭐⭐ **진단 순서 5단계** (고급1 전체의 결론)
  1. **공유 가변 상태가 있는가?** — 없으면 그냥 안전
  2. **없앨 수 있는가?** (무상태·불변) — 08편, 최선의 해결책
  3. **단일 필드의 가시성·순서만 필요한가?** → `volatile` (06편)
  4. **복합 갱신·검사 후 변경인가?** → `synchronized` (07편)
  5. **락이 여러 개 필요한가?** → **순서 통일** (09편)
  - 경계선: **"현재 값을 읽어서 그걸 기반으로 쓰는가"** — 그러면 ④, 단순 on/off 플래그면 ③.
- **면접 답변 3단 구조**: **문제 → 원인 → 해결**을 30초·세 문장으로. 암기가 아니라 사고 틀을 갖추는 게 목표.
  - 예) `count++`: "한 줄이지만 읽기·증가·쓰기 복합 연산입니다(문제). 두 스레드가 같은 값을 읽고 각자 저장하면 증가 하나가 유실됩니다(원인). `synchronized`나 `AtomicInteger`로 원자적으로 증가시켜 해결합니다(해결)."
  - 꼬리 질문 4종: ① `volatile int count++`가 왜 안전하지 않나 ② getter도 동기화해야 하나(→ 가시성 위해 같은 락으로) ③ 스프링 싱글턴 빈은 자동으로 안전한가(→ 아니오, 무상태 설계) ④ 락 쥔 채 외부 API 호출이 왜 위험한가(→ 처리량 급락)

## 코테 04 — 문자열

- **문제 상황별 도구 판단**

  | 상황 | 도구 |
  |---|---|
  | 문자 하나씩 확인 | `charAt(i)`, `toCharArray()` |
  | 개수 세기 | `int[26]`, `int[128]`, `HashMap` |
  | 계속 누적 | `StringBuilder` |
  | 특수문자 제거·패턴 검사 | `replaceAll()`, `matches()` |

  → 교재의 분류: 문자열 문제는 **① 하나씩 보는 문제 ② 개수를 세는 문제 ③ 조건에 맞게 다시 만드는 문제**로 나눈다.
- **`c - 'a'`의 원리**: `char`는 사실 **숫자**(ASCII). `'a'`=97, `'b'`=98 … 연속이므로 `c - 'a'`가 **0~25 인덱스**가 된다. 칸 번호가 곧 글자, 칸의 값이 개수. 되돌릴 땐 `(char)('a' + i)`. 숫자는 `c - '0'`.
- **선택 기준**: 소문자만 → `int[26]` / **대소문자·숫자·기호 섞임 → `int[128]`**(ASCII 값을 그대로 인덱스로, 변환 불필요) / 한글 등 → `HashMap`.
  - ⚠️ 대문자·숫자에 `c - 'a'`를 쓰면 음수 인덱스 → `ArrayIndexOutOfBoundsException`(언체크).
- ⚠️ **`split(".")` vs `split("\\.")`**: `split`의 인자는 **문자열이 아니라 정규식**. 정규식에서 `.`은 "아무 문자 하나"라 `split(".")`은 빈 배열이 된다. 진짜 점은 **`"\\."`**.
  - 같은 이유로 **`replace()`는 단순 문자열, `replaceAll()`은 정규식**.
- ⚠️ **`"".split()`이 길이 1인 함정**: `"".split("\\s+")`의 결과는 **길이 1인 `[""]`**. 그래서 공백만 있는 입력의 단어 개수가 0이 아니라 1로 틀린다.
  - 안전한 형태: `trimmed.isEmpty() ? 0 : trimmed.split("\\s+").length`
- **`replaceAll("[^a-z0-9]", "")`**: 두 번째 인자가 `""`면 **삭제**. `[ ]`는 "이 중 아무거나 하나", `-`는 범위, **대괄호 안 맨 앞의 `^`는 부정**(= 이것들 빼고 전부).
  - ⭐ `toLowerCase()`를 **먼저** 해야 한다. 안 하면 대문자가 "소문자가 아니다"로 걸려 지워진다.
  - 범위는 ASCII 순서 기준이라 `[a-x0-8]` 같은 것도 가능. 단 `[a-Z]`는 시작>끝이라 `PatternSyntaxException`(언체크). 대소문자는 `[a-zA-Z]`처럼 **두 범위를 이어붙여** 쓴다(구분자 없음).
- **양끝 포인터 팰린드롬**: `left=0`, `right=length-1`에서 시작해 `while (left < right)` 동안 비교, 다르면 즉시 `false`.
  - 뒤집기(`new StringBuilder(s).reverse()`) 대신 쓰는 이유 ① **추가 메모리가 변수 두 개뿐** ② **첫 글자에서 다르면 즉시 종료**(조기 종료).
  - 실전 조건(대소문자·특수문자 무시)은 `raw.toLowerCase().replaceAll("[^a-z0-9]", "")`로 **정리 후** 넘긴다. 이 조합이 교재의 핵심 템플릿.
- **`char` 비교는 `==`/`!=`** (기본형), `String` 비교는 `equals` (객체).

## 트러블슈팅

- **람다 안에서 체크 예외를 던질 수 없는 문제**
  - **증상**: `java: unreported exception java.lang.InterruptedException; must be caught or declared to be thrown`. `main`에 `throws InterruptedException`을 붙여도 안 없어짐.
  - **원인**: `Runnable.run()`의 선언에 `throws`가 없다. 람다는 그 `run()`을 구현하는 것이라, **원본에 없는 체크 예외를 던질 수 없다.** 람다 안은 `main`의 몸통이 아니라 `run()`의 몸통이므로 `main`의 `throws`가 적용되지 않는다.
  - **해결**: 람다 안에서 `try-catch`로 직접 잡고, `catch`에서 `Thread.currentThread().interrupt()`로 **인터럽트 상태를 복구**한다(빈 catch 금지).
  - **배운 점**: `throws`는 "부른 사람에게 떠넘기겠다", `try-catch`는 "내가 여기서 처리하겠다". **람다는 떠넘길 수 없어 종착역**이다.
