# 2026-10-23 (금) 능동회상 노트

## 복습 드릴 (OOD 02 SOLID · 코테 05)

### SOLID 다섯 원칙 — 원칙마다 확인하는 질문
- SRP: 이 클래스가 바뀌는 이유가 하나인가(변경 이유가 하나인가).
- OCP: 새 기능을 추가할 때 기존 코드를 고치지 않고 새 구현을 추가하는 것만으로 되는가.
- LSP: 하위 타입(새 구현)으로 바꿔 끼워도 호출하는 쪽이 깨지지 않는가(상위 타입의 계약을 지키는가).
- ISP: 쓰는 쪽(클라이언트)이 필요 없는 메서드까지 든 큰 인터페이스에 의존하고 있지 않은가.
- DIP: 업무 코드가 구체 기술(JPA·메일 구현) 대신 추상화(인터페이스)에 의존하는가. 판단법은 "서비스 코드에 어느 쪽 이름이 적혀 있나"입니다(구체 클래스 이름이면 약함, 인터페이스 이름이면 만족).
- 조회 화면이 조회만 쓰는데 취소·환불 메서드까지 든 큰 인터페이스에 의존하는 것은 ISP 문제입니다. 조회용·변경용으로 인터페이스를 나눕니다.
- OrderService가 생성자로 구체 클래스 JpaOrderRepository를 받으면 DI는 적용된 상태(밖에서 만들어 넘겨줌)지만 DIP는 약한 상태(서비스에 구체 클래스 이름이 적힘)입니다. OrderRepository 인터페이스를 받으면 둘 다 만족합니다.

### 코테 05 완전탐색
- 덩치 rank는 "나보다 몸무게·키가 둘 다 큰 사람 수 + 1"입니다. 1에서 시작해 더 큰 사람을 만날 때마다 1씩 올리므로, 둘 다 큰 사람이 2명이면 3등입니다.
- 카드 4장 중 순서 없이 3장을 고르는 경우는 4가지(한 장을 빼는 경우와 같음, i<j<k), 2장을 고르는 경우는 6가지(3+2+1, i<j)입니다. 순서까지 구분하면 순열(4×3×2=24)이 되므로 조합과 헷갈리지 않습니다.
- 후보 범위 순회는 정답 후보가 연속된 정수 범위에 있고 후보 하나를 검사하는 비용이 가벼울 때 씁니다. 작은 값부터 검사하다 처음 만족하는 값(가장 작은 답)에서 break 합니다.

## OOD 03 캡슐화와 응집도·결합도 (§1~§53, §54 이후는 Spring·JPA 학습 뒤 12/15)

### ① 큰 그림 (§1~§4)
- 이 장의 목표는 "높은 응집도, 낮은 결합도" 문장을 외우는 것이 아니라, 코드를 보고 "왜 이 코드들이 함께 있나, 무엇에 어떻게 의존하나"를 판단해 답할 수 있게 되는 것입니다.
- 응집도는 한 모듈 내부 요소들이 같은 책임·같은 변경 이유로 얼마나 관련되어 있는가이고, 결합도는 모듈 사이(외부 요소 사이)의 의존성, 즉 한쪽이 바뀔 때 다른 쪽이 얼마나 영향을 받는가입니다.
- 좋은 설계의 기본 방향: 같은 이유로 바뀌는 코드는 가까이 두고, 다른 이유로 바뀌는 코드는 경계로 나누고, 필요한 의존성은 명시하고, 내부 구현은 감추고, 안정된 계약으로 협력합니다. 목표는 의존성을 없애는 것이 아니라 필요한 의존성만 명확하고 안정적으로 만드는 것입니다.

### ② 응집도 (§5~§15, §18)
- 응집도가 높은 클래스는 하나의 책임(예: 주문 금액 계산)을 위해 필드와 메서드가 함께 쓰입니다. 낮은 클래스는 저장·CSV 출력·마케팅 분석·메일 발송처럼 변경 이유가 다른 일이 한 클래스에 섞여 있고, 흐름 조정이 아니라 각 일의 세부사항까지 다 알고 있습니다(Helper·Manager·Util 같은 모호한 이름이 신호).
- 응집도를 판단하는 질문: 책임을 한 문장으로 말할 수 있는가 / 필드들이 대부분의 메서드에서 함께 쓰이는가 / 메서드들이 같은 업무 규칙을 다루는가 / 한 정책 변경이 클래스 대부분을 함께 바꾸는가 / 이름이 모호하고 무관한 기능이 모였는가.
- 상태와 행동을 한 객체에 두는 이유: 상태를 바꾸는 규칙(예: 결제 완료면 취소 가능)이 객체 안에 있어야 외부가 getter·setter로 상태를 꺼내 판단하지 않고, 규칙이 바뀌어도 그 객체만 고치면 됩니다(order.cancel()).
- 같은 Member 데이터를 써도 저장·CSV 출력·마케팅 분석은 바뀌는 이유가 달라 분리 대상입니다(같은 필드 사용 ≠ 같은 책임). 반대로 여러 객체를 호출해도 하나의 유스케이스(주문하기)를 조정하는 애플리케이션 서비스는 응집될 수 있습니다. 응집도 낮은 서비스는 책임(변경 이유) 단위로 나눕니다.
- 가짜 응집도: EmailTrimService·EmailLowercaseService처럼 너무 잘게 쪼개면 클래스 하나하나는 응집돼 보이지만 흐름과 개념이 흩어져 전체 이해도가 떨어집니다. 좋은 경계는 독립적인 의미·독립적인 변경·독립적인 테스트 가치를 가집니다.
- 응집도 유형은 이름을 외우기보다 판단 도구로 씁니다. "왜 이 코드들이 함께 있나? 같은 책임과 변경 이유 때문인가(기능적 응집), 아니면 단지 같은 시점·같은 데이터·비슷한 이름 때문인가(약한 응집)"를 묻습니다.

### ③ 패키지 응집도 (§19~§21)
- 같은 업무 기능·같은 변경 이유·밀접한 협력·경계를 함께 쓰는 코드는 한 패키지에 둡니다(package-private으로 감추고 외부엔 하나의 기능 경계로 공개). 업무 기능·변경 이유가 다르거나, 의존 방향을 나눠야 하거나, 외부 기술 세부사항을 격리해야 하면 나눕니다.
- 계층별 패키지(controller/service/repository)는 처음 이해하기 쉽고 작은 프로젝트에 단순하지만, 한 기능을 바꿀 때 여러 패키지를 오가야 하고 기능 경계가 약해지며 package-private을 활용하기 어렵습니다. 기능별 패키지(order/, member/)는 한 기능의 코드가 한곳에 모여 패키지 응집도가 높고 경계가 분명합니다.

### ④ 결합도 기본 (§22~§25, §31)
- 결합도가 높으면 다른 클래스의 내부가 바뀔 때 나도 함께 고쳐야 하고(변경이 퍼짐), 낮으면 안정된 계약만 알기 때문에 상대 내부가 바뀌어도 영향이 적습니다.
- 결합도를 판단하는 질문: 상대의 내부 필드·자료구조를 아는가 / 구체 구현을 직접 생성하는가 / 호출 순서를 외부가 기억해야 하는가 / boolean flag로 상대 행동을 제어하는가 / 하나의 변경이 여러 모듈을 함께 고치게 하는가 / 테스트에 협력 객체가 많이 필요한가 / 패키지 순환 의존성이 있는가.
- 협력하려면 어느 정도 결합이 필요하므로 결합도를 0으로 만들 수 없습니다(결합도 0 = 협력 0). 목표는 불필요한 결합·내부 구현 결합을 없애고, 안정된 계약에 의존하고, 변경 방향을 통제하는 것입니다.

### ⑤ 코드에서 보이는 의존 형태 (§26~§30)
- 클래스·메서드·타입·패키지 이름도 의존성입니다. 이름이 바뀌면 호출자가 줄줄이 바뀌므로 saveToMysql 같은 기술 이름 대신 save 같은 안정적인 업무 중심 이름을 씁니다.
- 데이터 결합은 필요한 데이터만 넘기는 것(receipt.issue(orderId, paidAmount))이고, 제어 결합은 flag로 상대 내부 흐름을 지시하는 것(process(order, true, false, 3))입니다. flag가 많으면 호출자가 상대의 분기 규칙을 알아야 하므로 approve(order)·cancel(order)처럼 의도별 메서드로 나눕니다.
- public 필드·reflection·private 직접 수정·상대 내부 컬렉션 변경처럼 내부 구현에 직접 손대는 내용 결합, static 전역 가변 상태(GlobalConfig.testMode)에 기대는 공통 결합은 누가 언제 바꾸는지 알 수 없고 영향이 전체로 퍼져 테스트와 추적이 어렵습니다.
- 메서드 호출 자체는 정상적인 결합입니다. 문제는 호출자가 세부사항을 너무 많이 알 때로, open → authenticate → reserve → capture → close 순서를 외부가 알면 순서가 깨질 때 실패하므로 pay(command)처럼 한 메서드로 감쌉니다.

### ⑥ 기술에 대한 결합 (§32~§35)
- 구체 구현 결합: NotificationService 안에서 new SmtpEmailSender()를 하면 SMTP 교체와 단위 테스트가 어려우므로 NotificationSender 인터페이스를 생성자로 받습니다. 프레임워크 결합: @Entity·@Service·@Transactional 같은 애너테이션과 프레임워크 API에 대한 의존입니다(프레임워크 = 뼈대를 주고 내 코드를 불러 주는 것). 모두 나쁜 건 아니고 "이 타입이 프레임워크 밖에서도 의미가 있나, 테스트에 Spring Context가 꼭 필요한가, 도메인 규칙이 프레임워크 API에 묻히나"로 판단합니다.
- 강한 데이터베이스 결합 4가지: Service가 JPQL 문자열을 만듦 / Controller가 Entity를 직접 반환 / 업무 규칙이 DB trigger에만 있음 / 여러 서비스가 같은 table 구조를 직접 참조. 쿼리는 Repository 안에 둡니다.
- 외부 API(PG사) 결합에서 어댑터는 외부 PG사 응답 DTO를 내부 모델(PaymentResult)로 바꿔 도메인에 넘깁니다. PG사가 바뀌어도 어댑터만 고치면 됩니다.

### ⑦ 눈에 잘 안 보이는 결합 (§36~§40)
- 시간 결합은 특정 시점·생명주기에 맞춰 실행돼야 하는 의존(캐시 초기화 후 서버 시작, 커밋 후 이벤트 발행)이고, 순서 결합은 여러 연산의 선후 관계에 대한 의존입니다. 순서 결합은 순서를 아는 한 메서드 pay(command)에 모아 줄이고, 시간 결합은 메서드 이름·상태 객체·트랜잭션 이벤트·워크플로 객체로 드러냅니다.
- Map<String,Object> context를 여러 곳이 공유하면 key 이름 계약(문자열 오타), 타입 안정성 부족(Object 캐스팅), 누가 값을 바꾸는지 불명확이라는 세 가지 문제가 생깁니다(성능 문제는 아님). record PaymentContext처럼 이름과 타입이 정해진 객체로 바꿉니다.
- 자바 객체는 방향마다 필드가 따로라(Order.member, Member.orders) 양방향이면 양쪽 동기화·삭제 규칙·직렬화 순환·JPA 편의 메서드가 필요합니다. DB는 외래키 하나로 양쪽을 탐색할 수 있는 것과 다릅니다. 업무상 양방향 탐색이 정말 필요한지부터 확인합니다.
- order → payment → member → order처럼 의존이 돌면 독립 테스트와 패키지 분리가 어렵고 초기화 순서 문제와 변경 전파가 생깁니다. 스프링 생성자 주입에서 순환 참조 오류가 나는 것은 설계 문제를 일찍 발견하게 해 주는 신호로 받아들입니다.

### ⑧ 캡슐화와 결합도 (§41~§46)
- 정보 은닉: 외부가 order.lines().removeIf(...)처럼 자료구조와 규칙을 알면 내부를 바꿀 때 외부도 바뀝니다. order.removeCancelledLines()로 감추면 내부를 List에서 Set으로 바꿔도 외부 영향이 줄어듭니다.
- getter 자체는 나쁘지 않지만, 외부가 getStatus()로 읽고 setStatus()로 바꾸며 업무 판단까지 하면 외부가 내부 상태 표현에 결합됩니다. 컬렉션을 그대로 내주면 외부가 내부 리스트를 수정할 수 있어 캡슐화가 무너지므로 List.copyOf로 막고, 더 나아가 행동 API를 제공하는 편이 낫습니다.
- Tell, Don't Ask: 상태를 물어봐서(ask) 밖에서 판단하지 말고 객체에게 하라고 시킵니다(tell). if (order.getStatus() == PAID) order.setStatus(CANCELLED) 대신 order.cancel()입니다.

### ⑨ 디미터 법칙과 CQS (§47)
- 디미터 법칙의 직접적인 친구는 this, 매개변수로 받은 객체, 메서드 안에서 만든 객체, 자기 필드입니다. order.getMember().getAddress().getCity()처럼 반환값을 따라 남의 내부 구조를 계속 탐색하면 위반 후보입니다. stream().filter().map()이나 빌더 체이닝은 같은 추상화의 공개 계약을 이어 가는 것이라 위반이 아닙니다.
- DTO·값 객체라고 자동 예외는 아닙니다. 직접 받은 record(ShippingLabel)의 접근자를 한 단계 쓰는 것은 그 타입이 공개한 계약이라 괜찮고, 기준은 "호출자가 여러 중첩 객체의 구조를 연속으로 알아야 하는가"입니다. 값 객체 Money는 필드를 꺼내 계산하기보다 add() 같은 행동을 제공하는 편이 낫습니다.
- CQS: Command는 상태를 바꾸고 반환값이 없고(void), Query는 값을 반환하고 상태를 바꾸지 않습니다. applyAndGetRemaining처럼 둘을 섞으면 부작용을 예측하기 어렵습니다. 실용적 예외는 Queue.poll()·Iterator.next()·Map.put()으로, 조회와 변경을 한 번에 하는 것이 자료구조의 핵심 계약이라 허용됩니다(멀티스레드 원자성은 별개).
- 위임으로 감싸면 호출자가 알아야 하는 구조(구조 노출)가 줄어듭니다. N+1·SQL 조회 수는 위임과 상관없이 fetch join·entity graph·DTO 조회 같은 별도 조회 전략으로 해결합니다.

### ⑩ 정리 (§48~§53)
- 응집도를 높여도 결합도가 자동으로 낮아지지 않습니다. 관련 규칙을 잘 모아도 public API가 넓고 가변 상태를 노출하면 외부 결합이 높을 수 있습니다. 인터페이스는 결합도를 조절하는 수단 중 하나일 뿐이고, 의미 없는 1:1 인터페이스는 파일 수와 탐색 비용만 늘립니다. 다른 수단으로 작은 public API·package-private·불변 객체·DTO 변환·이벤트가 있습니다.
- 좋은 결합은 업무상 필요한 협력·명확한 타입·안정된 계약·단방향 의존·테스트 가능한 경계이고, 나쁜 결합은 상대 내부 구조 의존·전역 가변 상태·숨은 호출 순서 같은 것입니다.
- 안정된 의존성은 Java 표준 타입·업무적으로 안정된 값 객체·작고 명확한 포트이고, 불안정한 의존성은 외부 API 응답 DTO·프레임워크 내부 타입·자주 바뀌는 DB schema·여러 책임을 가진 거대 인터페이스입니다. 결합도는 의존성 개수가 아니라 변경 가능성과 영향 범위로 판단합니다.
