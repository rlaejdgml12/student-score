# 2026-08-11 (화) — 4주차: 자바 중급2 01~06 (제네릭·ArrayList·LinkedList·List추상화·Hash 원리)

## 01 제네릭 기본
- 타입 매개변수 vs 타입 인수: 타입 매개변수(`T`)는 클래스/메서드를 선언할 때 "어떤 타입인지는 나중에 정한다"고 자리만 잡아두는 것이고, 타입 인수(`String`, `Integer` 등)는 실제로 그 클래스를 사용할 때 `<>` 안에 채워 넣는 구체적인 타입이다.
- raw type과 unchecked 경고: `List` 처럼 `<>`를 아예 생략하고 쓰는 게 raw type. 컴파일러가 타입 안전성을 검사해주지 못해 "unchecked" 경고가 뜨고, 런타임에 `ClassCastException`이 날 위험이 있다.
- 바운디드 타입 매개변수 `<T extends Number>`: 타입 매개변수가 아무 타입이나 되는 게 아니라 `Number`(또는 그 자식)여야 한다고 제한을 거는 문법. 이렇게 해야 `T` 타입 값에 대해 `doubleValue()` 같은 `Number`의 메서드를 호출할 수 있다.

## 02 제네릭 심화
- 제네릭 메서드: 클래스 자체의 `<T>`와 별개로, 메서드 하나만을 위한 독립적인 `<T>`를 선언할 수 있다. 메서드 선언부 맨 앞(`static <T> ...`)에 붙인다.
- 와일드카드 `? extends` / `? super`: `T`는 "내가 직접 객체를 만들 때" 쓰는 것이고, `?`는 "이미 만들어진 걸 받기만 할 때" 쓰는 것. `? extends`는 그 타입이거나 그 자식 타입을 읽기만 할 때(생산자), `? super`는 그 타입이거나 그 부모 타입에 쓰기만 할 때(소비자) 사용한다.
- PECS 원칙: Producer Extends, Consumer Super — 값을 꺼내기만(생산) 한다면 `extends`, 값을 넣기만(소비) 한다면 `super`를 쓴다는 원칙.
- 제네릭의 불공변성: `Dog`이 `Animal`의 자식이어도, `List<Dog>`은 `List<Animal>`의 자식이 아니다. 제네릭 타입은 실제 타입 간의 상속 관계를 그대로 물려받지 않는다.
- 타입 이레이저 때문에 안 되는 것 3가지: ① `instanceof List<String>`처럼 제네릭 타입까지 포함한 instanceof 검사 ② `new T[]`처럼 타입 매개변수로 배열을 직접 생성 ③ static 컨텍스트(static 필드/메서드)에서 클래스의 타입 매개변수 `T`를 사용하는 것. 컴파일 후에는 제네릭 타입 정보가 지워지기(erasure) 때문이다.

## 03 ArrayList 원리
- 배열 기반 저장과 인덱스 조회가 O(1)인 이유: 배열은 메모리에 연속으로 붙어있어서, 인덱스만 알면 "시작 주소 + 인덱스 × 한 칸 크기"로 바로 주소를 계산해 접근할 수 있다.
- 동적 배열 증설: 배열이 꽉 차면 더 큰 새 배열을 만들어 기존 원소를 복사(grow)한다. 교육용으로는 보통 2배씩, 실제 OpenJDK는 약 1.5배(`oldCapacity + (oldCapacity >> 1)`)씩 늘린다.
- 중간 삽입/삭제가 O(n)인 이유: 중간에 값을 끼워 넣거나 빼려면, 그 뒤에 있는 원소들을 전부 한 칸씩 밀거나 당겨야 하기 때문이다.
- 분할상환(amortized) O(1)이란: `add()` 한 번 한 번을 보면 가끔(꽉 찼을 때) O(n)이 걸리는 grow가 일어나지만, 여러 번의 호출에 걸쳐 평균을 내면 결국 O(1)에 가깝다는 뜻. (당장은 헷갈렸던 "큰 수의 법칙"과는 다른 개념 — grow 비용을 여러 번의 삽입에 나눠서 갚는다는 의미.)

## 04 LinkedList 원리
- 노드/링크 구조: 배열 없이, 각 데이터(노드)가 "다음 노드가 어디 있는지"를 직접 참조(`next`)로 들고 있는 구조.
- 단일 연결 vs 이중 연결: 단일 연결은 `next`만, 이중 연결은 `next`와 `prev`를 둘 다 가진다. `java.util.LinkedList`는 실제로 이중 연결이라 앞뒤 어느 방향으로도 순회할 수 있다.
- Deque와 addFirst/addLast/pollFirst/pollLast: `Deque`는 양쪽 끝에서 넣고 뺄 수 있는 자료구조 인터페이스. `LinkedList`는 `first`/`last`를 직접 들고 있어서 양쪽 끝 삽입/삭제가 모두 O(1)이다.
- ArrayDeque를 순수 큐·스택 용도로 더 선호하는 이유: 배열 기반이라 노드마다 참조를 따로 둘 필요가 없어 메모리 오버헤드가 적고, 데이터가 메모리상 연속으로 붙어있어 캐시 지역성도 더 좋다.
- get(index)가 왜 O(n)인지: 인덱스로 바로 주소 계산이 안 되고, `first`나 `last` 중 가까운 쪽부터 노드를 하나씩 따라가야만 위치를 찾을 수 있기 때문이다.

## 05 List 추상화와 성능
- 인터페이스 의존 vs 구현체 의존: 변수 타입을 `ArrayList`가 아니라 `List`로 선언하면, 그 이후 코드는 `List`가 제공하는 기능에만 의존하게 되어 나중에 구현체(`ArrayList`↔`LinkedList`)를 자유롭게 바꿀 수 있다.
- 컴파일 타임 의존관계와 런타임 의존관계의 차이: `List<String> names = new ArrayList<>();`처럼 선언해도, `new ArrayList<>()`를 직접 호출하는 그 지점은 여전히 컴파일 타임에 `ArrayList`에 의존한다. 실행 시점에 구현체를 자유롭게 바꾸려면 생성자 주입 같은 별도 장치(DI)가 필요하다.
- DI와 인터페이스 의존의 관계: 필요한 객체를 스스로 만들지 않고 생성자 등을 통해 밖에서 받는 것이 DI. 인터페이스에 의존해두면 DI로 구현체를 바꿔 끼우기가 훨씬 쉬워진다(다만 DI에 인터페이스가 필수는 아님).
- ArrayList vs LinkedList 상황별 선택 기준: 인덱스 조회가 잦으면 ArrayList(O(1)), 위치를 이미 아는 상태에서 삽입/삭제가 잦으면 LinkedList(O(1)) 유리. 일반적인 기본 선택은 ArrayList.

## 06 Hash 원리
- 해시가 필요한 이유: List처럼 처음부터 순회하면 O(n)이 걸리는 조회를, 값을 숫자(hashCode)로 바꿔 저장 위치를 계산으로 바로 찾아가게 해서 평균 O(1)에 가깝게 만든다.
- hashCode()로 인덱스를 구하는 방법 — Math.floorMod: `Math.floorMod(hash, capacity)`는 결과가 항상 0 이상 capacity 미만이 되도록 안전하게 나머지를 구해준다.
- Math.abs(hash) % length가 완전하지 않은 이유: hashCode가 `Integer.MIN_VALUE`일 때 `Math.abs()`가 오버플로우로 여전히 음수를 반환하기 때문.
- 해시 스프레딩 — h ^ (h >>> 16): 해시값의 상위 16비트를 하위 비트에 XOR로 섞어서, 상위 비트의 차이도 인덱스 계산에 반영되게 만들어 충돌을 줄인다.
- 테이블 크기를 2의 거듭제곱으로 유지하는 이유: `(capacity - 1) & hash`라는 비트 연산이 `hash % capacity`와 결과가 정확히 같아지려면 capacity가 2의 거듭제곱이어야 하기 때문. 비트 연산이 나머지 연산보다 빠르다.
- 해시 충돌과 Java 8 이후 트리화: 서로 다른 값이 같은 버킷에 들어가는 게 해시 충돌. 한 버킷에 노드가 많이(대표적으로 8개) 쌓이면 연결 리스트 대신 트리 구조로 바꿔서 최악의 경우 조회 성능을 O(n)에서 O(log n)으로 개선한다.
- 로드 팩터 0.75와 threshold: threshold(=capacity × loadFactor)를 넘으면 테이블 크기를 2배로 늘리고 재배치(resize)한다. 0.75는 공간 활용과 충돌 최소화 사이의 균형점으로 정해진 기본값이다.

## 트러블슈팅 (막혔던 부분·에러)
- MyLinkedList의 `get()`에서 count 초기값을 잘못 잡아 인덱스가 한 칸씩 밀리는 버그, removeFirst에서 노드가 1개 남았을 때 NPE 나는 케이스를 놓쳤던 것 — 둘 다 힌트로 스스로 수정.

- 비트 연산(`>>>`, `^`, `&`)은 개념은 이해했지만 코드로 직접 짜는 게 부담스러워서, MyHashSet 2·3버전은 코드 대신 원리 문제로 대체.
