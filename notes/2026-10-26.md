## 스프링 01 스프링 입문과 IoC/DI

### ① UserDao와 세 가지 관심사 (§1~§3)
- JDBC로 회원을 저장하는 add()의 흐름: Class.forName으로 DB 드라이버를 로딩 → DriverManager.getConnection으로 Connection 획득 → c.prepareStatement로 SQL을 준비(값 자리는 ?) → ps.setString(번호, 값)을 ?마다 한 번씩(번호는 1부터, 컬럼이 3개면 3번) → ps.executeUpdate()가 실제로 저장하는 줄(기본 auto-commit) → ps.close(), c.close()로 자원 반환(만든 순서의 반대). 예외는 ClassNotFoundException(드라이버 클래스를 못 찾음), SQLException(DB 작업 오류)입니다.
- add() 안에는 세 가지 관심사가 뒤섞여 있습니다: ① DB 연결, ② SQL 실행, ③ 리소스 반환. 특히 연결 코드가 add()와 get()에 똑같이 복사되어 있어서(초난감 포인트) DB를 바꾸면 모든 메소드를 고쳐야 합니다.
- 관심사의 분리는 바뀌는 이유가 다른 것을 나누는 것입니다. OOD의 SRP(클래스가 바뀌는 이유는 하나)와 뿌리가 같은 생각이고, SRP는 클래스 수준의 표현, 관심사의 분리는 메소드·클래스·모듈 어느 수준에서도 쓰는 더 넓은 원칙입니다.

### ② 리팩토링 흐름 (§4~§8)
- 메소드 추출: 중복된 연결 코드를 getConnection() 메소드로 뽑아 한 곳에서만 고치게 했습니다.
- 템플릿 메소드 패턴(상속): abstract UserDao의 add()가 전체 흐름을 고정하고, getConnection()은 추상 메소드(빈칸)로 두어 NUserDao·DUserDao 같은 서브클래스가 채웁니다. 한계는 세 가지입니다: 단일 상속이라 다른 부모 클래스를 못 가짐 / 부모와 자식이 강하게 결합(부모가 바뀌면 모든 자식에 영향) / 컴파일 시점에 고정되어 실행 중 교체 불가.
- ConnectionMaker 인터페이스와 DConnectionMaker 구현체: UserDao는 인터페이스만 알고 연결 방식은 구현체가 맡습니다. 남은 문제는 UserDao 생성자에 new DConnectionMaker()가 있어 구현체를 여전히 안다는 점입니다.
- DaoFactory: 어떤 ConnectionMaker를 쓸지 정하는 관계설정 책임을 UserDao에서 DaoFactory로 옮기고, 생성자로 넣어 줍니다.
- OCP(확장에는 열려 있고 변경에는 닫혀 있음): ConnectionMaker 구현체를 새로 추가해도 UserDao 코드는 고치지 않습니다. 스프링이 OCP를 자동으로 만들어 주는 것은 아니고, 인터페이스 구조는 개발자가 설계하며 스프링은 객체 생성과 조립(IoC)을 맡습니다.

### ③ IoC와 컨테이너 (§9~§11)
- IoC(제어의 역전)는 객체 생성·관계설정·생명주기의 제어권을 코드 안에서 외부 조립자나 컨테이너로 넘기는 원리이고, DI는 그중 의존 대상을 외부에서 넣어 주는 대표적인 구현 방법입니다. IoC가 더 큰 개념입니다.
- @Configuration이 붙은 설정 클래스(DaoFactory)의 @Bean 메소드가 빈 정의이고 빈 이름은 메소드 이름입니다. new AnnotationConfigApplicationContext(DaoFactory.class)로 컨테이너를 만들고 context.getBean("userDao", UserDao.class)로 꺼냅니다. ApplicationContext는 범용 IoC 컨테이너로, DaoFactory와 달리 다양한 설정 방식·싱글톤 관리·생명주기 같은 부가 기능을 제공합니다.
- 스프링 빈은 기본이 싱글톤 스코프라 getBean을 몇 번 불러도 같은 객체이고, 일반 클래스의 DaoFactory.userDao()를 직접 부르면 매번 new로 새 객체가 생깁니다. GoF 싱글톤은 클래스가 private 생성자와 static getInstance(), static instance 필드로 스스로 하나만 관리하는 방식이고, 스프링은 평범한 public 클래스를 컨테이너가 하나만 만들어 관리하는 방식이라 테스트·상속 제약이 없습니다. 싱글톤 빈의 필드에 요청별로 달라지는 가변 상태를 두면 위험하고, final로 받은 불변 의존 필드는 안전합니다.

### ④ DI의 종류 (§12)
- DI의 세 요소: 코드에는 인터페이스 의존만 나타나고 / 실제 구현체는 컨테이너(외부)가 결정하며 / 생성자나 메소드로 주입됩니다. 방법은 생성자 주입, 수정자(setter) 주입, 일반 메소드 주입 세 가지이고, 필드 주입은 권장하지 않습니다.
- 생성자 주입이 우선인 이유: 필수 의존 대상이 객체 생성 시점에 확정되고, final 필드로 불변이 되며, 의존 대상이 빠진 객체가 아예 만들어지지 않습니다. 수정자 주입은 필수 의존이 안 들어간 불완전한 객체가 만들어질 수 있다는 단점이 있고, 대신 선택적 의존이나 나중에 바꿔야 하는 경우에 쓸 수 있습니다.

### ⑤ 최신 스프링 (§14)
- @Component(DAO용 종류가 @Repository)는 §10에서 @Bean 메소드가 하던 빈 등록을 클래스 위 표시로 대신하고, 컴포넌트 스캔이 표시된 클래스를 찾아 등록합니다. @Autowired는 그 생성자가 필요로 하는 빈을 컨테이너가 찾아 넣어 달라는 표시이고, 생성자가 하나면 생략할 수 있습니다(스프링 4.3+). DaoFactory 같은 설정 클래스는 필요 없습니다.
- @SpringBootApplication은 @Configuration + @ComponentScan + @EnableAutoConfiguration을 묶은 것으로, 그 클래스가 있는 패키지와 하위 패키지를 스캔합니다. SpringApplication.run(...)이 컨테이너를 만들고 조립합니다(§10의 AnnotationConfigApplicationContext 역할). getBean은 보통 직접 쓰지 않고 필요한 클래스가 생성자로 받습니다.
- @Bean과 @Component는 대체 관계가 아니라 상황별 도구입니다. 직접 쓴 클래스는 @Component 류로, 소스를 고칠 수 없는 외부 라이브러리 객체나 직접 조립 방식을 정해야 하는 것은 @Bean으로 등록합니다.

## JPA 01 JPA 소개와 패러다임의 불일치

### ① SQL을 직접 다룰 때의 문제와 JPA (§1~§3)
- SQL을 직접 쓰면 세 가지 문제가 생깁니다: 반복(조회·등록·수정·삭제마다 SQL 작성 → JDBC 실행 → 결과 매핑을 테이블마다 반복) / SQL 의존적 개발(필드 하나만 추가해도 등록·조회·수정 SQL과 매핑 코드를 전부 고침) / 엔티티 신뢰 불가(member.getTeam()이 값을 가질지는 객체만 봐서는 알 수 없고 실행된 SQL이 팀을 조인했는지에 달림).
- JPA는 SQL 대신 API를 호출하면 SQL을 만들어 줍니다: em.persist(member)는 INSERT, em.find(Member.class, id)는 SELECT, 조회한 객체에 setName만 하면 별도 update 메소드 없이 트랜잭션 커밋 때 변경 감지로 UPDATE가 만들어집니다. m.getTeam()처럼 연관 객체는 필요한 시점에 SELECT가 실행됩니다.

### ② 패러다임의 불일치 4가지 (§4~§7)
- 상속: 자바에는 상속(Album extends Item)이 있지만 테이블에는 없어서 ITEM·ALBUM 두 테이블로 나눠야 합니다. 그래서 객체 하나를 INSERT 두 개로 쪼개 저장하고, 조회할 때는 JOIN한 뒤 객체로 다시 조립해야 합니다. JPA는 조인 전략(InheritanceType.JOINED) 등으로 em.persist(album) 한 줄이면 이 일을 대신합니다(전략은 조인 / 단일 테이블(기본값) / 구현 클래스마다 테이블, 차이는 07장).
- 연관관계: 객체는 참조(member.team = Team 객체), 테이블은 외래 키(TEAM_ID 숫자)로 관계를 맺습니다. 저장할 때는 member.getTeam().getId()로 팀 객체를 숫자로 바꿔 INSERT하고, 조회할 때는 JOIN 결과의 숫자·문자열로 Team과 Member 객체를 만들어 연결해야 합니다. 테이블에 맞춰 teamId 숫자만 필드로 두면 변환은 쉽지만 member.getTeam()으로 객체를 따라가는 객체지향 방식을 포기하게 됩니다. JPA는 member.setTeam(team); em.persist(member);만 하면 참조를 외래 키로 바꿔 INSERT하고, 조회할 때도 참조로 다시 조립합니다.
- 객체 그래프 탐색: 객체는 참조를 따라 자유롭게 탐색할 수 있어야 하지만, SQL을 직접 쓰면 처음 실행한 SQL이 어디까지 조인했는지가 탐색 범위를 정합니다(MEMBER와 TEAM만 조인하면 getOrder()는 null). 그래서 getMember(), getMemberWithTeam()처럼 조회 메소드를 여러 벌 만들게 됩니다. JPA의 해결은 지연 로딩으로, 연관 객체를 실제로 쓰는 시점에 필요한 SELECT를 실행합니다(연관관계 매핑 필요, 영속성 컨텍스트가 끝난 뒤에는 실패할 수 있고, 접근마다 SQL이 추가로 나가는 N+1이 생길 수 있어 08장에서 다룹니다).
- 비교: DB는 기본 키로 행을 구분하지만, SQL을 직접 쓰면 getMember()를 호출할 때마다 new Member()로 새 객체가 만들어져 같은 기본 키여도 ==(동일성)는 false입니다. JPA는 같은 영속성 컨텍스트 안에서 같은 타입과 기본 키로 조회하면 항상 같은 인스턴스를 반환해 ==가 true입니다(같은 트랜잭션이라고 자동 보장이 아니라 같은 영속성 컨텍스트일 때). 영속성 컨텍스트는 JPA가 엔티티를 보관·관리하는 공간으로 03장에서 배웁니다.

### ③ ORM과 JPA (§8~§9)
- ORM은 객체와 관계형 DB를 대응(매핑)시키는 방식입니다. JPA(현재 표준명 Jakarta Persistence)는 ORM을 위한 자바 표준 명세(약속)이고 그 자체는 실행 코드가 아니며, 하이버네이트가 대표적인 구현체입니다(EclipseLink, DataNucleus도 있음). 구조는 자바 앱 ↔ JPA ↔ JDBC ↔ DB로, JPA는 JDBC 위에서 SQL 작성과 결과 매핑을 대신해 주는 층이고 내부에서는 JDBC가 쓰입니다. 패키지는 javax.persistence에서 jakarta.persistence(Persistence 3.0, 2020~)로 바뀌었습니다.
- JPA를 쓰는 이유 다섯 가지: 생산성(컬렉션처럼 저장·조회, DDL 자동 생성) / 유지보수(필드 하나 추가해도 SQL·매핑 코드를 일일이 고칠 필요가 줄어듦) / 패러다임 불일치 해결 / 성능 최적화 여지(같은 영속성 컨텍스트에서 find()로 같은 회원을 두 번 조회하면 SELECT는 한 번, 단 기본 키 직접 조회인 find()에만 해당하고 JPQL은 보통 SQL이 나감) / 데이터 접근 추상화와 벤더 독립성(방언만 바꿔도 상당 부분 동작하지만 식별자 생성 전략·컬럼 타입·네이티브 쿼리 같은 벤더 종속 부분은 여전히 영향을 받으므로 표준 범위에서 영향을 줄여 준다고 이해).

### ④ 오해 정리 (§10)
- ORM을 써도 SQL과 DB 지식은 필요합니다: 객체-테이블 매핑을 올바르게 하려면 객체와 관계형 DB를 모두 알아야 하고 테이블 설계와 SQL 지식도 여전히 필요합니다. N+1 문제는 SQL 한 번으로 N건을 조회한 뒤 연관 데이터를 위해 SQL을 N번 더 실행하는 문제입니다. SQL 매퍼(마이바티스)는 개발자가 쓴 SQL과 객체를 매핑해 주므로 SQL 의존이 남고, ORM(JPA)은 매핑만 해 두면 SQL 자체를 생성해 줍니다. 복잡한 통계 쿼리는 JPA의 네이티브 SQL을 쓰거나 마이바티스·JdbcTemplate을 함께 쓰는 것이 실무에서 흔합니다.
