## 고급2 08 — 락과 DB의 경계

- 실행자(ExecutorService) 생명주기를 **하나의 흐름**으로 정리 — 생성 → 제출 → 결과 수거 → `try-finally`로 반드시 종료.
- `merge()`로 빈도수 집계하는 패턴(`map.merge(key, 1, Integer::sum)`).
- ⭐⭐ **한 JVM의 경계** — `synchronized`나 `volatile` 같은 자바의 락은 **같은 JVM 프로세스 안에서만** 유효하다. 서버가 2대면 각 서버가 별개의 락을 가지므로, 자바 락만으로는 두 서버 사이의 동시성 문제를 못 막는다.
- 여러 서버에 걸친 동시성 문제는 **DB의 원자적 쿼리**(`UPDATE ... SET count = count - 1 WHERE count > 0`)나 **낙관적 락**(버전 체크)/**비관적 락**(`SELECT ... FOR UPDATE`)으로 해결해야 한다.

## 고급3 01 — 동작 매개변수화

- **동작 매개변수화**: 실행할 로직 자체를 매개변수로 넘겨서, 메서드 하나로 다양한 동작을 수행하게 만드는 설계 기법.
- ⭐ **"동작의 값화"**: 자바에서 코드(동작)를 마치 값처럼 변수에 담고 메서드에 전달할 수 있게 된 것 — 이게 람다의 본질적 의미. "무엇을 할지"를 데이터처럼 다룰 수 있다는 것.

## 고급3 02 — 함수형 인터페이스

- **SAM(Single Abstract Method)**: 추상 메서드가 딱 하나뿐인 인터페이스 — 람다가 대입될 수 있는 자리.
- `@FunctionalInterface`: SAM 규칙을 강제로 검사해주는 애너테이션(추상 메서드가 2개 이상이면 컴파일 에러로 미리 잡아줌).
- **괄호 규칙 3종**: 매개변수가 없으면 `()`, 하나면 괄호 생략 가능(`x -> ...`), 여러 개면 `(x, y) -> ...`.
- **대상 타입(target type)**: 람다 자체는 타입이 없고, 대입되는 변수·매개변수의 타입(어떤 함수형 인터페이스인지)에 따라 람다의 의미가 결정된다.
- `default`/`static` 메서드는 인터페이스 안에 있어도 **추상 메서드로 세지 않으므로** SAM 규칙을 깨지 않는다.
