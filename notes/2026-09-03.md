## 고급1 05 — 공유 자원과 Race Condition

- **공유 가변 상태**: 여러 스레드가 함께 읽고 쓰는, 변하는 데이터. 판단 기준은 **`new`가 몇 번 실행되나** — 한 번이면 공유, 스레드마다 실행되면 공유 아님.
  - 스택은 스레드마다, 힙은 전부 공유. 단 **힙에 있다 ≠ 공유된다** — 같은 객체를 여럿이 가리켜야 공유.
  - 함정: 람다가 캡처한 **지역 변수**도, 바깥에서 `new`가 한 번만 됐다면 공유다.
- **경쟁 상태(race condition)**: 결과의 올바름이 실행 순서·타이밍에 의존하는 상태. 순서를 통제 못 하니 결과도 실행마다 달라진다.
- **count++ 3단계 분해**: ① `count` 읽기 → ② 1 더하기 → ③ `count`에 쓰기 (**read-modify-write**). 이 사이에 끼어들면 **갱신 유실(lost update)**.
- **원자성(atomicity)**: 더 이상 **쪼갤 수 없는** 하나의 단위로 실행되어, 중간에 다른 스레드가 **끼어들 수 없는** 성질.
- **한 줄로 쓰였다고 원자적인 게 아니다**: 원자성은 **소스 코드의 줄 수**가 아니라 **중간에 끼어들 수 있는가**로 판단한다.
  - `count = 5` → 쓰기 하나라 원자적. `count = count + 1` → 아님.
  - 예외: `long`·`double`은 대입조차 쪼개질 수 있다.
- **검사 후 변경 문제**: `if (balance >= amount)`로 검사하고 `balance -= amount`로 변경하는데, 그 **사이**에 끼어들면 검사 결과가 무효가 된다. 둘 다 통과해서 **출금이 두 번 성공**.
  - → **검사와 변경 전체**를 하나의 원자적 단위로 묶어야 한다. 변경만 원자적으로 만들어도 소용없다.
- **테스트 통과 ≠ 안전**: 정상 결과가 나온 건 우연히 안 겹친 것뿐. 부하가 커지거나 코어 수가 다른 서버에 배포되면 깨진다. 안전성은 **실행 결과가 아니라 코드 구조**로 판단.
- **불변 조건(invariant)**: 프로그램이 올바르다면 항상 참이어야 하는 규칙("잔액은 0 이상", "한 좌석의 예약자는 최대 한 명"). 경쟁 상태가 이걸 깨뜨리고, 동기화의 목표는 이걸 지키는 것.

### ⭐ 오늘 두 번 헷갈린 것 — 위험 구간의 크기
`sleep`을 **위험 구간 밖**에 두면 충돌 확률이 **내려가고**, **검사와 변경 사이**에 두면 위험 구간 자체가 커져 확률이 **올라간다**.

> 위험한 건 「시간이 오래 걸리는 것」이 아니라 **「공유 데이터를 만지는 순간」**이다.

## 고급1 06 — 메모리 가시성과 volatile

- **가시성 문제**: 한 스레드가 바꾼 값을 다른 스레드가 **못 볼 수 있다**. 값이 깨지는 게 아니라 **최신 값이 전달되지 않는** 문제 — 원자성과 **다른 축**.
  - "안 바뀐 것"이 아니라 **"안 보이는 것"**. `main`은 진짜로 바꿨다.
- **전형적 증상**: `while (running)` 루프가 플래그 변경을 못 보고 **무한 루프**.
- **JMM (Java Memory Model)**: "어떤 조건에서 한 스레드의 쓰기가 다른 스레드의 읽기에 **보이도록 보장되는가**"를 정한 **자바 언어 수준의 계약**. 하드웨어와 무관하게 적용된다.
- **happens-before**: A가 B보다 happens-before면 → **A의 결과가 B에게 반드시 보인다**는 보장 관계. 단순한 시간 순서가 아니다.
  - 동기화를 배운다 = **필요한 곳에 happens-before 관계를 만들어 준다**.
- **volatile이 보장하는 것 2가지**
  1. **가시성** — 쓴 값이 이후 읽기에 보인다
  2. **순서 보장(재배치 제한)** — 컴파일러·CPU가 코드 순서를 몰래 바꾸는 것을 제한
- **volatile이 보장 못 하는 것**: **원자성**. `volatile int count`라도 `count++`는 여전히 유실된다. 최신 값을 보게 해줄 뿐, 읽기-증가-쓰기를 묶어주지 않는다.
- **volatile을 써도 되는 3가지**: ① 종료·일시정지 **플래그** ② **초기화 완료 신호** ③ **완성된 객체 참조의 교체**
  - 공통점: **읽어서 계산해 다시 쓰는 게 아니다**.
- **"캐시에서 직접 읽는다"가 부정확한 이유**: 실제 캐시 동작은 **하드웨어마다 다르고**, 자바가 보장하는 건 하드웨어 동작이 아니라 **JMM의 happens-before**다. 캐시는 비유로만, 근거는 JMM에.

### 판단 문장
> 읽기만 하거나 값 하나를 **통째로 갈아끼우는 것** → `volatile`
> 지금 값을 읽어서 **그걸 바탕으로 새 값을 만드는 것** → 락 필요

## 고급1 07 — synchronized와 임계 영역

- **임계 영역(critical section)**: 한 번에 **한 스레드만** 실행해야 하는 코드 구간.
- **모니터 락**: **모든 자바 객체가 하나씩 가지고 있는 열쇠**. `synchronized`는 그 열쇠를 집었다 놓는 것.
  - ⭐ **서로 다른 객체의 모니터는 서로를 막지 못한다.**
- **synchronized 메서드 vs 블록**
  - 메서드: 메서드 **전체**가 임계 영역. 열쇠는 자동으로 정해짐
  - 블록: `synchronized(lock) { }` — **열쇠를 직접 지정**하고 범위를 좁게 잡아 대기 시간을 줄임
- ⭐ **같은 상태에는 같은 락**: 같은 공유 상태를 **다른 락**으로 보호하면 두 락이 **서로를 못 막아** 동시에 임계 영역에 들어간다. `synchronized`를 붙였는데도 경쟁 상태가 남는다. (교재: "초보가 가장 자주 만드는 동기화 버그")
- **인스턴스 락 vs 클래스 락**

  | | 열쇠 | 보호 대상 |
  |---|---|---|
  | 인스턴스 `synchronized` | `this` (그 객체) | 인스턴스 필드 |
  | `static synchronized` | 클래스의 `Class` 객체 | `static` 필드 |

- **static 필드를 인스턴스 락으로 감싸면**: 인스턴스마다 열쇠가 달라 여러 스레드가 동시에 들어온다. 공유되는 `static` 필드가 그대로 깨진다.
- **private lock 객체를 쓰는 이유**: `this`는 외부에 노출된 객체라 **남이 `synchronized(myObject)`로 내 락을 잡을 수 있다**. 외부에 안 보이는 `private final Object lock`을 쓰면 동기화 정책을 클래스가 온전히 통제한다.
- **재진입(reentrant)**: 이미 열쇠를 쥔 스레드는 **같은 열쇠를 다시 잡을 수 있다**. 안 그러면 `synchronized` 메서드가 다른 `synchronized` 메서드를 부를 때 자기가 자기를 막는다.
- **volatile vs synchronized**

  | | 가시성 | 원자성 | 비용 |
  |---|---|---|---|
  | `volatile` | ✅ | ❌ | 락 없음 — 아무도 안 기다림 |
  | `synchronized` | ✅ | ✅ | 대기 + 문맥 전환 비용 |

## 코테 03 — 배열과 기본 반복

- **향상된 for문의 한계**: 값을 **복사해서** 받으므로 반복 변수를 바꿔도 원본 배열은 안 바뀐다. **인덱스가 필요하거나 원소를 수정하려면 기본 for문.**
- **최댓값 초기값을 0으로 두면 안 되는 이유**: 배열이 전부 음수면 조건에 한 번도 안 걸려 **배열에 없는 0이 답이 된다.** → `int max = arr[0]`
  - `>` = 처음 등장한 최댓값 위치 / `>=` = 마지막 등장 위치
- **합계를 long으로**: `int`는 약 21억. 넘으면 **에러 없이 조용히 음수로** 돌아간다.
- **배열 대입 vs clone()**
  - `int[] b = a` — 복사가 **아예 아님**. 주소만 베낌 → 완전히 같은 배열
  - `a.clone()` — 1차원은 **진짜 새 배열**
- ⭐ **2차원 clone()이 위험한 이유**: 2차원 배열은 **"배열의 주소를 담은 배열"**. `clone()`은 **바깥 껍데기만** 새로 만들고 **행 주소는 그대로 베껴** 원본과 행을 공유한다(**얕은 복사**). → **09 DFS/BFS의 `visited` 방문 배열 버그로 직결.**
- **2차원에서 deep이 붙은 메서드**
  - `Arrays.deepToString(board)` — 내용 출력
  - `Arrays.deepEquals(a, b)` — 내용 비교 (`Arrays.equals`는 행의 **주소**만 비교해 내용이 같아도 `false`)
  - **복사만 deep 버전이 없다** → 직접 `for`문으로 행마다 `clone()`

## 트러블슈팅

**① `unreported exception InterruptedException; must be caught or declared to be thrown`**

`Thread.sleep()`이 던지는 `InterruptedException`(대기 중 인터럽트 시 발생하는 **체크 예외**)을 아무도 책임지지 않아서. 책임질 자리가 **두 군데**였다.

- `reserve()`/`withdraw()`에 `throws InterruptedException` 선언 → 위로 넘김
- 그런데 `Runnable`의 `run()`은 `throws`가 없어 **더 위로 못 넘김** → **람다 안에서 `try-catch`**로 끝내야 함
- `catch`에서는 `Thread.currentThread().interrupt()`로 **인터럽트 상태 복구** (빈 catch 금지)

> **체크 예외 처리는 「코드 조각마다」 따로다.** `userA`에서 처리했다고 `userB`가 넘어가지 않는다.
> 결정 기준은 "어디서 던지느냐"가 아니라 **"누구의 시그니처를 구현 중이냐"**.

**② `volatile` 없는 무한 루프가 재현 안 됨**

`VolatileFlagExample`에서 `volatile`을 빼도 정상 종료됐다. **JIT 컴파일러의 루프 최적화 시점에 의존**해서 환경마다 다르기 때문(교재도 이 구간만은 실패 가능하다고 명시).

> **안 걸렸다고 안전한 게 아니라, 이 컴퓨터에서 이번에 운이 좋았던 것.**
> `volatile`을 붙이는 근거는 "터지는 걸 봤으니까"가 아니라 **"JMM이 보장해 주지 않으니까"**.

**③ `static volatile class Worker` — `volatile`을 클래스에 붙임**

`volatile`은 **필드에만** 붙는다. 붙을 자리는 `flag`.

**④ `worker.run()`을 직접 호출**

새 스레드가 안 생기고 `main`이 직접 루프로 들어가, `shutdown()`에 영원히 도달 못 함. → `new Thread(task)` + `start()`. (8/28에 세 번 막혔던 자리 — 이번엔 힌트만으로 해결)

**⑤ `withdraw`에 `synchronized`와 `synchronized(lock)`을 겹쳐 씀**

열쇠를 두 개 잡는 셈. 동작은 하지만 ① 정책이 둘로 갈려 「하나의 상태, 하나의 락」이 흐려지고 ② 락을 여러 개 잡는 습관은 **교착 상태(09장)** 로 이어지며 ③ `private lock`을 쓴 이유(외부가 `this`를 잡는 것 차단)가 무색해진다.
